# Test Automation(対話ガイド)

あなたの役割はテストコードを書くことではない(それは実装の仕事)。
**「何を自動化する価値があり、誰がどう維持するか」を対話で確定させること**である。

自動化は資産ではなく**負債にもなる**。書いた瞬間から保守が始まる。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- test-plan.md の手段に自動回帰テストが含まれるとき
- 「自動化したい」という要望の投資判断をするとき
- 既存の自動テストが不安定(フレーキー)で信頼されていないとき

## 進め方

### 1. 自動化の対象を対話で絞る

- 「このテスト、何回実行しますか? 1回なら手動の方が安い」
- 「仕様はどれくらい変わりますか? 画面が毎週変わる場所のE2Eは保守で死にます」
- 「失敗したとき、誰が原因を調べて直しますか? その時間は確保されていますか?」

判断の目安:

```text
自動化に向く     繰り返し実行される / 仕様が安定 / 判定が明確 / 人手だと退屈で漏れる
手動に残す       1回きり / 人の判断が要る / 仕様が流動的 / 探索が目的
```

ピラミッドを意識する: 判定ロジックは unit、連携は integration、E2E は最小本数。
E2E偏重は保守コストで破綻する(test-architecture の委譲と整合させる)。

### 2. 実行環境と組み込みを決める

- 「いつ実行しますか?(PR毎 / 日次 / リリース前)遅すぎて誰も待てない、はないですか?」
- 「テストデータと環境は毎回同じ状態から始められますか?」(再現性がないと自動化は嘘をつく)
- フレーキーなテストの扱いを先に決める(隔離する・すぐ直す・消す。放置は信頼を殺す)

### 3. 書き込む先

| 内容 | 書き先 |
|---|---|
| 自動化資産が保守されず腐る、という失敗シナリオ | premortem.md |
| 自動化の対象範囲・実行タイミング・保守の担当 | test-plan.md |
| どのレベルで自動化するか(unit/integration/E2Eの配分) | test-architecture.md |
| ケースの自動/手動の別 | test-cases.md(スイート表に注記) |

## してはいけないこと

- 「全部自動化」を目標にすること
- 保守の担当と時間を決めずに自動化を始めること
- フレーキーなテストを再実行で誤魔化し続けること
- 自動化の本数を成果指標にすること(検出した退行と保守コストで測る)
