# テスト技法カタログ

観点・パラメーターを導くときに引く。全観点に技法が要るわけではない。
「この技法を使った」と test-design.md に書くとき、ここの名前を使う。

参照: ISTQB CTFL v4.0 4章 / CTAL-TA v4.0 3章 / ISO/IEC/IEEE 29119-4(いずれも目次レベル確認)

## いつどれを使うか(早見)

| 状況 | 技法 |
|---|---|
| 入力の範囲・区分がある | 同値分割 → 境界値分析 |
| 条件の組み合わせで結果が決まる | デシジョンテーブル |
| 状態によって同じ操作の結果が変わる | 状態遷移 |
| パラメーターが多く総当たりが爆発する | ペアワイズ |
| データのライフサイクルを追いたい | CRUDテスト |
| 業務の流れで確認したい | シナリオテスト |
| 仕様がなく経験で攻める | エラー推測 / 探索的テスト(専用Skill) |

## 各技法

### 同値分割(Equivalence Partitioning)

同じ扱いを受ける入力群を1つの区分とみなし、区分ごとに代表値1つで試す。
有効区分だけでなく**無効区分**(エラーになるべき入力)を忘れない。

### 境界値分析(Boundary Value Analysis)

区分の境界とその両隣を試す。バグは境界に集まる。
例: 上限14桁 → 13 / 14 / 15 を試す。境界が仕様のどこで決まるかを必ず確認する。

### デシジョンテーブル(Decision Table)

条件の組み合わせ(列)ごとに期待動作を表にする。
全列を書いてから、ありえない列を理由付きで消す。**消した理由が仕様の穴の発見になる**。

### 状態遷移(State Transition)

状態と遷移を図にし、網羅基準(全状態 / 全遷移 / 遷移の組)を決めて試す。
**図に描かれていない遷移**(この状態でこの操作をしたら?)こそ聞く。
複雑な場合は model-based-testing Skill へ。

### ペアワイズ(Pairwise)

全組み合わせではなく「任意の2パラメーターの組」を網羅する。
組み合わせ爆発の抑制に使うが、**仕様上の依存関係(このブランドはこの桁数)がある場合は
機械的に適用せず、依存を先に反映する**。

### CRUDテスト

データごとに生成・参照・更新・削除の4操作が揃っているかを表にする。
「削除されたデータを参照する画面」のような**操作間の隙間**が見つかる。

### シナリオテスト

業務の開始→分岐→例外→完了の流れで確認する。機能単位のテストでは出ない
「つながりの壊れ方」を狙う。受け入れ確認と相性がよい(acceptance-testing Skill)。

### エラー推測(Error Guessing)

経験から「ここが壊れそう」を直接挙げる。根拠(過去の障害・よくあるミス)を
書けるなら observation として有効。体系的技法の代替ではなく補完。

## 判定を明確化する型(期待結果が一意に書けないとき)

判定方法を「人の判断」に倒す前に、以下で「明確」にできないか確認する。

| 型 | 判定の仕方 | 例 |
|---|---|---|
| 不変条件 | 常に成り立つべき性質で判定 | 在庫は負にならない / 合計は明細の和 |
| 比較 | 別実装・旧バージョン・手計算と突き合わせ | 移行前後で同じ入力→同じ集計 |
| 統計・閾値 | 固定した評価セットに対する率で判定 | 正答率95%以上(ai-testing Skill参照) |

それでも書けないものが「人の判断」である。
