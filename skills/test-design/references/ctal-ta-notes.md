## 0章: TAの役割

- TA=顧客のビジネスニーズ寄りの役割。機能テスト中心+ユーザー向け非機能(ユーザビリティ・適応性・インストール性・相互運用性)に貢献。ブラックボックス技法と経験ベースを使う。
- 対象テストレベル: システム / 受け入れ / システム統合。

## 1章: テストプロセスでのTAのタスク

- テスト分析: テストベースの完全性・テスト容易性を評価し早期フィードバック。**口頭情報も含む**。テスト条件は段階的に詳細化してよい(「画面xの機能」→「画面xは1桁短い口座番号を拒否」)。ステークホルダーとテスト条件をレビューする。
- テスト設計: 高位/低位どちらのケースが適切かを領域ごとに決め、**明確な合否基準を必ず特定**。ケースは書いた本人以外(実行者・開発者・監査者)が理解できること。
- テスト実装: 手順にはケースの手順に加え**前提条件のセットアップ・事後確認・リセット手順**を含める。環境の準備確認はスモークテストで行うのが最良。
- テスト実行後の評価: 欠陥クラスターの認識 / **失敗した自動テストを手動で再実行して偽陽性を排除** / 学んだことから追加テストを提案 / 新リスクの識別。異常の原因は欠陥とは限らない(前提不足・テストデータ誤り・スクリプトや環境の欠陥・仕様の誤解)。

### 1.3.1 高位ケースと低位ケース

- 高位(論理的)ケース: どのテスト条件を覆うかを抽象的に示す。網羅の確認に向く。低位(具体的)ケース: 具体的な前提・入力・期待結果・事後条件を持つ。
- 高位→低位は「値を埋める」以上の作業(概念→技術への変換)で、しばしばテスト実装まで遅延される。**実務のケースの多くは保守性と理解性のトレードオフでハイブリッド**(一部具体・一部抽象)。
- 高位ケースのまま実行時に具体化する使い方もある(探索セッションのチャーター目標を導く等)。

### 1.3.2 テストケースの品質基準(9基準)

- **正確性**: 基となるテスト条件を正しく検証できる。
- **実行可能性**: 実際に実行できる。
- **必要性**: 各ケースが明確なテスト目的を持つ(タイトルに表れる)。重複を避け、テスト不要なものにケースを作らない。
- **理解可能性**: 作者以外が読める言葉と形式。自明なことは説明しない。複雑なケースは分割。
- **追跡可能性**: テスト条件・要件・リスクへ遡れる(保守の前提)。
- **一貫性**: 用語・書式・構造の統一(用語集の活用)。
- **正確な記述(Precision)**: 解釈が一意。「適宜」「必要に応じて」「いくつか」等の曖昧語は偽陽性/偽陰性を生むため禁止。
- **完全性**: 必要な属性(テストデータ、疑いなく比較できる期待結果)が揃っている。
- **簡潔性**: 粒度はテスト条件に対応させる。**少数のカバレッジ項目に絞った小さいケースが望ましい**(原因特定が楽・組み合わせ自由・失敗しても他を塞がない)。

### 1.3.4 テストオラクルの決定

- オラクル問題: 費用対効果の合うオラクルが得られない状況。要因: データの複雑さ・非決定性(AI)・確率的挙動・要件の欠落や曖昧さ。
- 解決策(Barr et al. 2014): **疑似オラクル**(同じ仕様の独立実装: レガシー・簡易版) / **モデルベース**(モデルから期待出力を生成) / **プロパティベース**(入力と期待結果の関係=性質で判定) / **メタモルフィックテスト** / **人間オラクル**(高価だが探索的テストでは好まれる)。
- アサーション(テストコードまたは対象内)で自動オラクルを実装できる。
- → test-design の「判定を明確化する型」と直結する内容。不変条件≒プロパティベース、比較≒疑似オラクル。

### 1.3.5 テストデータ要件

- **本番類似性**: 本番データは現実的だが変動が乏しい。合成データは変動を制御できるが実データ特有の欠陥を見逃しうる。本番データがない場合はペルソナで現実的な利用者像からデータを導く。
- **機密性**: 仮名化/匿名化、GDPR等の規制順守。
- **目的**: 前提条件と期待結果を決めるデータ(システム日時・権限・エンティティ間の関連を含む)。
- **カバレッジ基準との整合**: 選んだ技法の網羅に必要なデータ(**無効データも**)を揃える。
- その他: 構造化形式(CSV/JSON) / ケース変更に耐える追跡可能性 / **低位ケースへのハードコード回避(ロジックとデータの分離)** / 依存データは生成手順が要る / 欠けるサービスはサービス仮想化 / **時間依存データの経年劣化**に注意。
- 1.3.3 環境要件: 項目ごとに ID・記述・責任者・必要期間・**忠実度(本番との差)** を書く(ISO 29119-3)。

## 2章: リスクベースドテストでのTAのタスク

- リスク評価の要因: 使用頻度と機能の重要度 / ビジネス目標への影響 / 金銭・環境・評判の損害 / **テストベースの品質** / 法規制。リスクは対象全体で一様でないため、テストアイテム単位に分けて評価する。
- 回帰テスト選択(手動実行では決定版の技法が無い、状況で選ぶ): リスクベース選択 / **履歴ベース**(過去に欠陥を出した・類似変更に敏感だったテスト+長く実行していないテスト) / カバレッジベース / 要件トレーサビリティマトリクス(間接影響も) / **運用プロファイルベース**(利用パターンで選ぶ) / 影響分析(変更された構成要素と相互作用するテスト)。
- 複数技法の併用が普通。サイクルごとに選択の有効性を分析し、効いた技法を残し効かない技法を入れ替える。

## 3章: テスト分析とテスト設計(615分・最重量)

ブラックボックス技法を**データ系 / 振る舞い系 / ルール系**の3分類+経験ベースに整理(v4.0の新分類)。

### 3.1 データ系

- **ドメインテスト**(EP/BVAの多変数一般化): 区分の境界をON/OFF/IN/OUT点で覆う。閉境界(≤,≥,=)のON点は境界上、開境界(<,>,≠)のON点は区分内の最近傍。簡易ドメイン網羅=境界ごとにON+OFF、信頼ドメイン網羅=ON+OFF+IN+OUT(検出力が大幅に高い)。=は ON1+OFF2、≠は OFF1+ON2。
- **組み合わせテスト**: ベースチョイス網羅(重要な基準値の組を作り、1パラメーターずつ他の値に置換)とペアワイズ網羅。値が多いパラメーターは先にEPで削減。**約97%の障害は1〜2パラメーターの相互作用で起きる**(Kuhn 2004)→ペアワイズの根拠。
- **ランダムテスト**: 確率分布から入力を選ぶ。妥当性確認には運用プロファイル分布、検証には利用非依存分布。**自動オラクルがほぼ必須**。網羅基準が無いので終了は実行数/時間で決める。ドメイン知識が乏しい時・大量データが要る時に有効。ファズ・カオスエンジニアリングにも応用。

### 3.2 振る舞い系

- **CRUDテスト**: CRUDマトリクス(列=エンティティ、行=機能)を作る。**完全性テスト=静的**(全エンティティにC/R/U/Dが揃うか。欠けは要調査の異常)+**一貫性テスト=動的**(機能間でエンティティが一貫して扱われるか。**未作成の読み取り等ネガティブも含める**)。CRUD網羅=実行した操作数/マトリクス総操作数。更に「各Uの後に全Rを確認」等の厳格化も可。データ完全性違反・アクセス制御欠陥を狙う。
- **状態遷移テスト**(CTFLへの追加分): **Nスイッチ網羅**(N+1連続遷移。0スイッチ=全有効遷移。Nで指数増加するため2スイッチ以上は高リスク時のみ)と**ラウンドトリップ網羅**(開始=終了となるループを覆う。欠陥検出効果の実証あり)。
- **シナリオベーステスト**: アクティビティ図またはユースケース(**主シナリオ/拡張(別経路で目標達成)/例外(目標未達)** の3種)でモデル化。ループがあれば**単純ループ網羅**(0回・1回・複数回・最大回数)。シナリオ内の変数にEP/BVAを重ねると1シナリオ複数ケースになる。E2E・受け入れと相性が良い。

### 3.3 ルール系(状態に依らないルールの検証)

- **デシジョンテーブル**(CTFLへの追加分): 「−」(don't care)による**最小化**と、**チェックサム手順**(最小化表の各ルールが元の表の何列分かを数えて合計。元の列数より小=網羅漏れ、大=重複/実行不能列。**一致しても等価の保証はない**)。レビュー観点: 一貫性・実行可能性・完全性・正しさ・重複なし。**リスクが高い場合は最小化せず全列で網羅測定**。
- **メタモルフィックテスト(MT)**: 既存のソースケースから**メタモルフィック関係(MR)**=「入力の変化が期待結果にどう反映されるか」でフォローアップケースを生成。例: 平均値関数で「並べ替えても平均は同じ」「全要素をx倍すれば平均もx倍」。ソース+フォローアップを1手順にまとめて関係が成り立つかで合否判定。**個々の期待結果が書けないオラクル問題下でも使える**(AIシステムのテストで推奨技法)。ランダムテストと組み合わせて大量生成可。網羅基準は未確立。

### 3.4 経験ベース

- **テストチャーター**: ミッションの軽量書式 **「Explore(対象)With(リソース)To discover(知りたい情報)」**(Hendrickson)。追加情報の例: セッション時間・目的・スコープ(やらないことも)・開始条件・**限界(製品が決してしてはならないこと)**・環境・過去の欠陥や未解決の疑問・制約と規制。**書き込む情報量が探索の自由度を決める**(目的だけなら自由度大、技法指定で制約増、「絶対できないこと」の明記は偽陽性報告を減らす)。セッション中の疑問・観察・次のテストのアイデアはセッションシートに記録。
- **チェックリスト**: read-do型(具体的な確認項目を順に実施)と do-confirm型(思考を導く問い。探索の発想源)を区別。項目は yes/no/N.A. で答えられる問いにし、優先度を付ける。出典は経験者の知見・**欠陥ライブラリーや欠陥分類(Beizer等)**・リスク分析。完成はなく、見逃した欠陥で更新し続ける。
- **クラウドテスト**: 多様な環境・実ユーザー視点・スケール性が利点。品質のばらつき・調整コスト・機密性・重複/偽陽性報告の管理が難点。技法適用の代替ではなく環境カバレッジの補完。

### 3.5 技法の選択

- 選択要因: テスト目的 / **プロダクトリスク(技法ごとに狙える欠陥種が違う**: データ系=データ処理・計算・組み合わせ、振る舞い系=要件漏れ・処理欠陥、ルール系=ロジック欠陥**)** / テストベースの形(モデルがあればそれを使う。オラクルが得られなければMTか経験ベース) / 再発欠陥の知識 / テスト担当者の技能(不慣れな技法を重要案件で使わない。ドメイン知識がなければ探索は非効率) / SDLC / 契約・規制 / 時間と予算。
- 技法の組み合わせ例: 状態遷移のガード条件にBVA / シナリオ中の変数にドメインテスト / シナリオ+ラウンドトリップ網羅で業務の循環を検証。
- テスト設計自動化(MBT等)の利点: モデリング自体が仕様の欠陥を暴く / 複雑な網羅基準が使える / モデルが単一の真実の源になり保守が楽 / トレーサビリティ向上。リスク: **モデルに現れないテスト条件の見落とし** / モデル保守コストの過小評価 / 関係者がモデルを理解できない。

## 4章: 品質特性のテスト(60分・概要のみ)

- 機能適合性の3下位特性を区別: **完全性**(求められたものが全部あるか。トレーサビリティが鍵)/ **正確性**(結果が正しいか。**有効なオラクルの確保が核心**)/ **適切性**(実装がユーザーの目的を果たすか。探索的・協調ベースが最適)。
- ユーザビリティ(レビュー・テストセッション・アンケートにTAが貢献)、フレキシビリティ(適応性・インストール性。**環境の組み合わせに組み合わせテスト**)、互換性(相互運用性=データ変換・解釈・プロトコルの欠陥を狙う)。

## 5章: ソフトウェア欠陥予防(225分)

- 欠陥予防の3本柱: 混入を防ぐ(QA)/ **後工程への流出を防ぐ(フェーズ封じ込め)** / 再発を防ぐ。効果測定: DRE(リリース前除去率)・PCE(同一フェーズ内除去率)・品質コスト。

### 5.2 フェーズ封じ込め

- **モデリングによる仕様の欠陥検出**: 非形式な仕様をモデル化する行為自体が、不完全・不整合・曖昧を効率的に暴く(レビューは原形のまま検査するがモデリングは変換するのが強み)。データ系モデル→区分の重なり・空白、振る舞い系(CRUDマトリクス・状態モデル・シナリオモデル)→ライフサイクル不整合・遷移漏れ・デッドロック・例外処理漏れ、ルール系→業務ルールの欠落・矛盾・冗長。
- **モデル自体の欠陥**の例: 状態図=到達不能状態・非決定的挙動、アクティビティ図=行き止まり・同期漏れ、デシジョンテーブル=重複・実行不能・欠落列。
- **レビュー技法5種**: アドホック(準備不要だが技能依存・重複報告多)/ チェックリストベース(観点の固定化・属人性排除。**過去に見逃した欠陥で更新**)/ シナリオベース(ユースケース等をドライラン。書かれたシナリオの外も見る)/ ロールベース(ユーザー種別・ペルソナごとに担当を割る)/ **パースペクティブベースドリーディング**(視点ごとに読み、**その視点の成果物を実際に作ってみる**: テスターなら仕様からドラフトの受け入れテストを作り情報不足を暴く。重複が少なく深い)。

### 5.3 再発の防止

- **テスト結果分析による検出力改善**(TA-5.3.1, K4): 予測vs実績の欠陥クラスター比較(乖離した領域を増強。重大度で重み付け)/ **DDP分析**(そのレベルで検出できたはずの流出欠陥に限定して数え、期間や除外基準を固定する)/ 構造カバレッジ分析 / **テストギャップ分析**(最近の変更でテストされていない箇所を優先。低カバレッジ全部より効率的)/ 欠陥到着パターン分析(Rayleighモデル等と比較し、増えるべき局面で低止まりならテストが弱い兆候)。
- 注意: **失敗テスト数≠欠陥数**(多対多。複数テストが同一欠陥を検出/1テストが複数欠陥を検出)。テストの重要度と欠陥の重大度も別物。
- **欠陥分類によるRCA支援**: 個別欠陥ごとのRCAは高コスト→分類して型ごとにRCAする。分類はSDLC全体で統一して初めて機能する。手法: ODC(直交属性で報告時と修正時に分類)/ IEEE 1044 / 重大度分類 / 欠陥分類学(Beizer)。技法: 5 Whys・特性要因図・パレート分析。
