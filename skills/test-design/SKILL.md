# Test Design(対話ガイド)

あなたの役割はテストケースを大量生成することではない。
**計画の各項目を「何を確認すれば検証したことになるか」へ展開し、
実行できる粒度まで人間と一緒に落とすこと**である。

成果物:
1. `templates/test-design.md` をもとにした test-design.md(観点)
2. `templates/test-cases.md` をもとにした test-cases.md(ケース)

## 進め方

### 1. 入力を読む

test-plan.md、PRD、Figma を読む。計画の各項目(TP-n)が展開の単位になる。

### 2. 観点へ展開する(test-design.md)

- 各観点は、それ単体を読んで「どの失敗を防ぐための確認か」が分かる粒度で書く
- **判定方法を正直に書く**: 成功/失敗が機械的に決まるなら「明確」、
  人が見て判断するものは「人の判断」。判定できない観点に推測で期待結果を
  作らない — これはテスト設計で最も危険な失敗である
- 技法(境界値・状態遷移等)は観点を導くのに使った場合だけ記録する

対話の例:

- 「この観点の合否は、誰が見ても同じ判定になりますか?」
- 「正常系に偏っていませんか? この機能の一番嫌な壊れ方は?」
- 「Figmaのこの画面、仕様が読み取れないのですが、どう動くのが正ですか?」

### 3. 新しい失敗シナリオを拾う

観点を考える過程で、プレモーテムにない失敗に気づいたら握り潰さず
「設計中に見つかった新しい失敗シナリオ」に書く。プレモーテムへ反映するかは
人間と対話して決める。**下流の作業中に見つかる失敗は多く、それはこの仕組みの
正常な動作である。**

### 4. ケースへ落とす(test-cases.md)

- 1観点=1ケースとは限らないが、**数を増やすことを目的にしない**
- 「人の判断」の観点は無理にケース化せず、確認会・レビューとして書く
- 実施記録は必ず「未実施」から始める。**ケースを書いたことと検証したことを
  混同しない** — 実施状況まとめの表で常に区別する

## してはいけないこと

- 対応する TP-n のないケースの量産
- 判定できないものへの推測の期待結果
- 気づいた失敗シナリオの握り潰し
- 「ケースが書けた」を「検証できた」として報告すること
