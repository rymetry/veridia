# Test Design(対話ガイド)

あなたの役割はテストケースを書くことではない(それは test-cases Skillの仕事)。
**計画の各項目を「何を確認すれば検証したことになるか」という観点へ、
人間と一緒に展開すること**である。

成果物: `templates/test-design.md` をもとにした test-design.md

## 進め方

### 1. 入力を読む

test-plan.md、test-architecture.md、PRD、Figma を読む。
計画の各項目(TP-n)が展開の単位、アーキテクチャのグループ(A-n)が観点の置き場所になる。

### 2. 観点へ展開する

- 各観点は、それ単体を読んで「どの失敗を防ぐための確認か」が分かる粒度で書く
- **判定方法を正直に書く**: 成功/失敗が機械的に決まるなら「明確」、
  人が見て判断するものは「人の判断」。判定できない観点に推測で期待結果を
  作らない — これはテスト設計で最も危険な失敗である
- 技法(境界値・状態遷移等)は観点を導くのに使った場合だけ記録する。
  技法の選び方・使い方に迷ったら `references/test-techniques.md` を読む
  (判定方法を「明確」にできないか確認する型も同ファイルにある)。
  オラクル・テストデータ要件・欠陥予防の深掘りは `references/ctal-ta-notes.md`(CTAL-TA v4.0精読)

- 各観点に置き場所(A-n)を付ける。**どのグループにも置けない観点が出たら、
  無理に押し込まずアーキテクチャの見直しを提起する**

対話の例:

- 「この観点の合否は、誰が見ても同じ判定になりますか?」
- 「正常系に偏っていませんか? この機能の一番嫌な壊れ方は?」
- 「Figmaのこの画面、仕様が読み取れないのですが、どう動くのが正ですか?」

### 3. パラメーターと組み合わせを絞る

入力・状態・環境で結果が変わる観点について、変える要素と値候補を決める。

- **全組み合わせをそのまま試さない。** 技法(境界値・ペアワイズ等)や仕様の理解で絞る
- **絞った理由を必ず書く。** 理由のない絞りは漏れと区別できない
- 仕様に書かれていなくてもバグが出そうな要素(連打・同時操作・空値・境界日時)を
  対話で確認して追加する

対話の例:

- 「この機能の結果を変えるものは、入力以外に何がありますか?(状態・時刻・権限)」
- 「この組み合わせ、全部やると何通いになりますか? どこを固定できますか?」
- 「値の境界(桁数・上限・期限)は仕様のどこで決まっていますか?」

### 4. 新しい失敗シナリオを拾う

観点を考える過程で、プレモーテムにない失敗に気づいたら握り潰さず
「設計中に見つかった新しい失敗シナリオ」に書く。プレモーテムへ反映するかは
人間と対話して決める。**下流の作業中に見つかる失敗は多く、それはこの仕組みの
正常な動作である。**

### 5. 次フェーズへ渡す

観点とパラメーターが固まったら test-cases Skillへ。判定方法が「人の判断」の
観点はケース化せず確認会になること、組み合わせの絞り方を申し送る。

## してはいけないこと

- テストケース(手順・入力値・期待結果の組)まで書いてしまうこと
- 対応する TP-n のない観点を残すこと(必要性を対話で確認する)
- どのグループ(A-n)にも置けない観点の無理な押し込み
- 理由を書かずに組み合わせを絞ること
- 判定できないものへの推測の期待結果
- 気づいた失敗シナリオの握り潰し

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
