## 第1章 GenAI基礎(100分)

- AIスペクトラム: シンボリックAI(ルールベース)→ 古典ML(特徴量選択+訓練が必要)→
  深層学習 → GenAI。GenAIの利点は「追加訓練なしでテスト作業に直接使える事前学習済みモデル」。
  その代償がハルシネーション等のリスク(3.1章)という構図
- **「plausible is not necessarily correct」**(1.1.2の明文)。Transformerは統計的にもっともらしい
  次トークンを予測するだけ。非決定性は推論の確率的サンプリングとハイパーパラメータに由来
- LLM分類: Foundation(汎用・要適応)/ Instruction-tuned(指示追従)/ Reasoning(多段推論向き)。
  タスクの推論負荷で使い分ける。SLM=小型軽量モデルも選択肢
- コンテキストウィンドウ: 大きいほど長文(大きなテストログ等)に強いが計算コストが増す
- テスト向けLLM能力(1.2.1): 要件分析(曖昧さ・矛盾・欠落の指摘、確認質問の生成)、
  テストケース生成、**テストオラクル生成(期待結果)**、テストデータ生成、スクリプト生成・改善、
  結果分析(要約・重大度分類)、文書作成。インタラクション形態はAIチャットボット vs LLM組込テストツールの2系統

## 第2章 プロンプトエンジニアリング(365分・最大の章)

### 2.1 構造化プロンプト6要素と3大技法

- **6要素**: Role(役割/ペルソナ)・Context(テスト対象の背景)・Instruction(命令形で明確に)・
  Input data(ユーザーストーリー、AC、スクリーンショット等)・Constraints(制約)・Output format(出力形式)
- **3大技法**(6要素構造と組み合わせる):
  - プロンプトチェイニング: タスクを中間ステップに分解し、**各ステップの出力を人間が検証してから次へ**。
    複雑で精度が要る作業向き(テスト分析・設計・自動化)
  - Few-shot: 例を複数提示(zero-shot=例なし、one-shot=1例)。反復的・出力形式が固定の作業向き
    (Gherkin、キーワード駆動、定型レポート)
  - メタプロンプティング: LLM自身にプロンプトを生成・改善させる。新しいタスクのプロンプト作りに。
    「AIとのペアリング」の一形態と位置付け
- 併用パターン: メタで初期プロンプト作成 → few-shotで例を強化 → チェイニングで分割検証(2.2.5)
- システムプロンプト=会話全体の不変ルール(役割・制約)、ユーザープロンプト=毎回の指示。分けて設計する

### 2.2 テスト作業別の適用

- テスト分析: テストベースの欠陥(曖昧・矛盾・不完全)の指摘、テスト条件生成、リスクベースの優先度付け、
  カバレッジ分析(要件↔テスト条件のマッピング)、テスト技法の提案。**入力の質が出力の精度を直接決める**
- テスト設計・実装: テストケース生成、合成テストデータ(本番類似・プライバシー保護)、スクリプト生成、
  実行スケジュール最適化。演習は「AC→ケース生成→カバレッジ表で網羅性を検証させる」2段構え
- 自動回帰テスト: キーワード駆動スクリプト生成、変更影響分析による絞り込み、セルフヒーリング
  (UI/API変更への自動追従)、レポート自動生成、欠陥レポート+根本原因分析。
  「GenAIは間違える。リスクに応じて生成物を必ず確認」と本文に明記
- モニタリング・コントロール: メトリクス生成・傾向分析・ダッシュボード・自然言語サマリー

### 2.3 評価メトリクスとプロンプト改善

- **7メトリクス**: Accuracy(専門家作成物・要件との照合)/ Precision(目的に対する正しさ)/
  Recall(関連ケースの網羅、例: 同値パーティション被覆)/ Relevance & Contextual Fit(テストベース整合)/
  Diversity(エッジケース・挙動の多様さ)/ Execution Success Rate(生成スクリプトがそのまま動く率)/
  Time Efficiency(検証込みの時間対効果)
- **非決定性ゆえ、メトリクスは統計的に有意なデータに基づくこと**(1回の出力で判断しない)
- プロンプト改善技法: 反復修正 / A/Bテスト / 出力エラー分析 / ユーザーフィードバック統合 /
  長さ・具体度の調整。チーム内で**プロンプトライブラリを共有**し標準化する

## 第3章 リスク管理(160分)— Veridia規律の主根拠

### 3.1 ハルシネーション・推論誤り・バイアス

- 定義: ハルシネーション=事実誤り・無関係な生成(架空のケース、存在しないACの検証ケース)。
  推論誤り=論理構造の誤解釈(LLMは真の論理推論でなくパターンマッチ。計画・優先度付けで顕在化)。
  バイアス=訓練データ由来の偏り(非英語圏の過小代表、非機能テストの過小生成など)
- 非決定性が修正を困難にする: 一度直っても別の会話で再発する
- **識別手法**(3.1.2): ハルシネーション → クロス検証(文書・要件・既知挙動との突合)、専門家確認、
  出力間の整合性チェック。推論誤り → 論理フローのレビュー、**出力テスト(生成ケースを実際に実行して確認)**。
  バイアス → テスト戦略に対する代表性レビュー、テストタイプの偏り(非機能の過小)の点検。
  実施の深さは**タスクのリスクレベルに応じて**決める
- **緩和手法**(3.1.3): 完全なコンテキスト提供 / チェイニングで分割し中間検証 / 曖昧でないデータ形式 /
  タスクに適したモデル選択 / **複数LLMでの相互比較**。補完としてRAGとファインチューニング(4章)
- **非決定性の緩和**(3.1.4): temperature を下げる(一貫性↑・多様性↓のトレードオフ)、
  random seed 固定(対応実装のみ)。完全な再現性は保証できない → 出力検証の一部自動化で補う

### 3.2 データプライバシー・セキュリティ

- リスク: 意図しない機微情報の露出、データ利用の制御不能(同意なく保存・処理)、GDPR等の法令違反
- 攻撃ベクター(3.2.2の表): データ流出(長大プロンプトで訓練データ片を引き出す)/
  リクエスト操作(画像で文脈を逸らしハルシネーション誘発)/ データポイズニング(偽評価の注入)/
  悪意あるコード生成(バックドア・不正IPへの通信路)
- 緩和: データ最小化・匿名化/仮名化・暗号化とアクセス制御・利用ポリシーと教育。
  加えて**生成物の体系的レビュー(人間評価が本質)**、複数LLM比較評価、
  機密度に応じた実行環境選択(商用セキュア/セキュアクラウド/自組織内ホスト)、定期監査。
  Security Engineer・法務・CTO/CISOの関与を強く推奨

### 3.3–3.4 環境影響・規制

- エネルギー: 画像1枚生成≒スマホ満充電相当の例。不要なモデル呼び出しを控えるのが基本策。
  タスク特性と適正サイズのモデル選択が消費を左右する
- 規制・標準: ISO/IEC 42001(AIマネジメントシステム)、ISO/IEC 23053(ML利用AIの枠組み)、
  EU AI Act(リスク分類・透明性義務)、NIST AI RMF(公平性・透明性・セキュリティ)

## 第4章 LLM活用テスト基盤(110分)— 4.1含め全節確認済み

- **4.1.1 アーキテクチャ**: フロントエンド+バックエンド+LLM(API or 自組織ホスト)の多層構成。
  バックエンドが認証・データ取得・プロンプト準備・**出力の後処理(テスト条件との整合を確認してから提示)**を担う。
  データ源はリレーショナルDB(構造化テストデータ)+ベクトルDB(埋め込みによる意味検索)
- **4.1.2 RAG**: 文書を256–512トークン程度にチャンク化 → 埋め込み化しベクトルDBへ →
  クエリと意味的に類似のチャンクを検索し、それを根拠(グラウンディング)として生成。
  最新の仕様・要件・既存テストデータに整合した出力を得る手段 = ハルシネーション緩和策の一つ
- **4.1.3 LLMエージェント**: ツール(関数)呼び出しで外部システムを操作。自律型 / 半自律型(定期的な人間監督)。
  複数エージェントの協調=オーケストレーション。**エージェントもLLM同様にハルシネーション・推論誤り・
  バイアスを抱える** → 結果の自動検証か、クリティカルな作業には半自律型を使う
- 4.2 ファインチューニング: 組織固有の形式・用語への適応。SLMなら低コスト。課題=訓練データ品質・
  過学習・不透明性・計算資源。LLMOps: チャットボット利用 / GenAI搭載ツール / 内製の3方式で運用設計が変わる

## 第5章 組織導入(80分)

- シャドーAI(未承認ツールの利用)のリスク: セキュリティ・データプライバシー欠陥、法令・規格違反、
  知的財産の不明確さ(ライセンス不明ツールでの著作物処理)。対策=戦略と導入ステップの明文化
- GenAI戦略の要点: 測定可能な目標(生産性・サイクル短縮・品質)、モデル選定、入力データ品質、教育、
  効果測定メトリクス(2.3.1)、**プロセスガイドライン(機微データ規則・「何をAIで生成したか」の透明性義務・
  生成テストウェアのレビュー付き品質ゲート)**
- モデル選定基準: タスク性能(自組織ベンチマーク+2.3.1メトリクス)・ファインチューニング可否・
  経常コスト(トークン数×頻度で見積る)・コミュニティ/サポート。テスト特化ベンチマークは少ない(TESTEVAL等)
- 導入3フェーズ: Discovery(教育・実験)→ Initiation(ユースケース特定・優先度付け)→
  Utilization & iteration(統合・継続測定)。ユースケースごとに並行進行可。雇用不安への早期対処も明記
- 役割の変化: テスター → AI支援テストスペシャリスト(生成物の検証・プロンプト改善・プロンプトライブラリ保守)。
  テストマネージャー → AIテスト戦略・AIリスク管理・人間とAIエージェントの混成チーム管理

   議論するとき Accuracy/Recall/Diversity/Execution Success Rate 等は即使える具体語彙
2. **識別手法の対応表**(3.1.2): ハルシネーション→クロス検証、推論誤り→出力テスト(実行して確かめる)、
   バイアス→テストタイプの偏り点検。規律1「突き合わせ確認」を実務手順に具体化でき、
   検証の深さを「リスクレベルに応じて」決める原則も併せて示せる
3. **透明性義務+品質ゲート**(5.1.2): 「何をAIで生成したかを明示し、生成テストウェアには
   レビュー付き品質ゲートを設ける」。Veridiaの「根拠」列と直結し、規律5(導入の対話)の
   チェック項目として簡潔に足せる
