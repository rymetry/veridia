# Usability Testing(対話ガイド)

あなたの役割は画面の良し悪しを裁定することではない。
**「誰にとっての使いやすさを・どの方法で・いつ評価するか」を対話で確定させること**である。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- quality-characteristics で Interaction Capability が採用されたとき
- 「使われないこと」が失敗シナリオにあるとき(操作性が原因になりうる場合)
- アクセシビリティ要件(社内規程・法令・WCAG)があるとき

## 進め方

### 1. 3つを混同しない

```text
ユーザビリティ      目的の作業を効率よく達成できるか
UX                 利用全体の体験(期待・感情も含む)
アクセシビリティ    能力や環境が異なる人でも利用できるか
```

どれを問題にしているかで評価方法が変わる。対話で特定する。

### 2. 評価方法を選ぶ

| 方法 | 向くもの | Veridiaでの受け皿 |
|---|---|---|
| レビュー(専門家・チェックリスト) | 明白な問題の早期検出。アクセシビリティ基準 | 確認会(test-cases.md のR表) |
| ユーザビリティテスト(実利用者に操作してもらい観察) | 実際のつまずきの発見 | 確認会+探索セッション |
| アンケート(満足度の定量) | リリース後の総括的評価 | Evidenceとして記録 |

対話の例:

- 「実際の利用者に触ってもらう機会を作れますか? 誰を何人呼べますか?」
  (短縮形なら3〜5人・会議室でも発見は多い。0人と3人の差が最も大きい)
- 組織のUX成熟度が低いうちは、レビューよりユーザビリティテストを優先する
  (レビュー結果は「ただの意見」として退けられやすい。実利用者のつまずきは実証として通る)
- 「初めて使う人が、説明なしで最初の◯◯を完了できるべきですか?」
- 「アクセシビリティは何に準拠しますか?(社内規程 / WCAG のレベル)」
  アクセシビリティ要件がある場合は `references/accessibility-checklist.md` を読む

### 3. 判定方法を正直に

- 使いやすさの合否は大半が**人の判断**である。test-design.md で無理に「明確」としない
- ただし一部は明確化できる: 「タスク完了率」「所要時間」「WCAG基準の合否」。
  できるものは数値・基準に落とす
- 問題点だけでなく**うまくいっている点も記録する**
  (「直すべきでない箇所」が伝わり、報告も受け入れられやすくなる)

### 4. 書き込む先

| 内容 | 書き先 |
|---|---|
| 「使われない」系の失敗シナリオの具体化 | premortem.md |
| 評価方法と実施時期(実利用者の確保は制約に直結) | test-plan.md |
| 観点(タスク達成・迷い・アクセシビリティ) | test-design.md |
| 確認会の設計(誰が・何を・どう記録) | test-cases.md のR表 |

## してはいけないこと

- 開発者自身の「使いやすいと思う」を評価の代わりにすること
- 全画面の網羅レビュー(価値に直結する導線に絞る)
- アクセシビリティを最後に回すこと(構造の問題は後から直せない)

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
