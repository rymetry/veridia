## 第1章 基本概念

- ユーザビリティ = 特定の利用状況で特定の利用者が、有効性・効率性・満足性をもって目標を達成できる度合い(ISO 9241-210)。
  - 有効性「やりたいことができるか」/ 効率性「速く解決できるか」/ 満足性「使っていて快適か」
- **仕様通りに動いてもユーザビリティ問題は起こる**(例: 手順が煩雑=効率性、見た目が安っぽい=満足性)。
  安全性が重要なシステムでは死傷にもつながる
- 利用状況は4要素: 利用者 / タスク / 機器 / 環境(物理的・社会的・技術的)。同じ製品でも文脈で評価が変わる
- UXはユーザビリティを包含し、**利用前・利用中・利用後**の知覚と反応すべて(広告、サポート対応、遅延の連絡なども対象)
- アクセシビリティ評価は障害のある利用者との直接対話に焦点。効率・満足より**バリアの理解**を優先する
- **形成的評価(定性)**: 設計・プロトタイプ段階で問題を見つけ設計を導く。**総括的評価(定量)**: 実装前後に
  有効性・効率性・満足性を測定し、要件充足を判定する。どちらも反復可能
- 人間中心設計: 分析→設計→評価→反復。プロトタイプ(紙スケッチ可)への評価は安上がりで早い
- アジャイル向きの評価: RITE(問題発見と解決策が明確になり次第すぐUIを直し、次の被験者で確認。
  **1人観察しただけで変更してよい**)/ カフェ等での15分以内のクイックテスト / 曜日固定のweeklyテスト / レビュー

## 第2章 リスク

- 製品リスク例: 使えず返品・サポート殺到・SNSで不満拡散・強制利用によるストレスと生産性低下・健康/金銭被害
- プロジェクトリスク例: **評価が遅すぎて直す時間がない** / 経営層が結果を「主観」と無視 /
  評価者が「警察」化して些末な指摘を誇張 / テスト環境が現実と乖離(高性能PC・小さすぎるデータ・割り込みなし)
- リスク評価の観点: 利用者数・利用者層・利用頻度・タスク失敗時の損害・事業上の重要度・外部への見え方

## 第3章 標準

- ISO 9241-110: 対話の7原則(タスク適合性・自己記述性・期待一致・学習適合性・可制御性・エラー許容性・個人化適合性)。
  ヒューリスティクスに似るが一般的すぎて評価にはやや使いにくい
- ISO 9241-171: ソフトウェアアクセシビリティ指針(140以上)。ISO 25066: ユーザビリティ評価報告書のCIF書式
- UIガイドラインがないと「何が容認できないか」を決めにくい(例: ログオンに10ステップは妥当か?)
- WCAGはA/AA/AAAの3レベル。**シラバスはAA採用を推奨**。法制度の例: 英Equality Act 2010、米ADA・リハビリテーション法508条
- 注意: シラバスが参照するのはWCAG 2.0(2008)。現行は2.2まで進んでいるため、
  アクセシビリティの実務は references/accessibility-checklist.md と一次資料(w3.org)を優先

## 第4章 ユーザビリティレビュー(評価法1)

- 6ステップ: (1)準備(目的・方法・レビューア選定) (2)任意で作者が説明(バイアス注意) (3)**各自が単独で**評価し記録
  (4)合議でコンセンサス形成(**合意された指摘のみ報告**。1人だけの思い込みを除去) (5)報告 (6)レポート作成
- 単独評価の前に問うこと: 誰が・なぜ使うか、利用者の目標は何か、利用者はどう違う視点で見るか
- 3種: 非公式レビュー(資格不要・経験と常識ベース)/ エキスパートレビュー / ヒューリスティック評価
- ヒューリスティック評価はNielsenの10原則(システム状態の可視化、実世界との一致、ユーザーの制御と自由、
  一貫性、エラー予防、再認>想起、柔軟性と効率、ミニマルデザイン、エラー回復支援、ヘルプ)などの
  **確立されたリストに指摘を紐づける**。直感で見つけて後付けするのは誤用。自作ヒューリスティクスは避ける
- リスク: 意見ベースなので意見の衝突になりやすい / 些末なガイドライン違反ばかり見て重大な有効性・効率性の
  問題を見逃す / 声の大きい人の意見が通る

## 第5章 ユーザビリティテスト(評価法2)— 最重量の章

- 3ステップ: 準備(計画・被験者募集・スクリプト・タスク定義・**パイロットセッション**)→ セッション実施 → 結果伝達
- テスト計画は**1〜2ページで十分**。目的・対象ユーザー群・技法(思考発話)・被験者数・スケジュール・
  費用(謝礼含む)・場所・結果の伝え方。ステークホルダーがレビューして承認する
- **ユーザビリティテスト固有の目的**: 「この製品に深刻な問題があるとステークホルダーに実証して見せる」
  (レビューやアンケートにはできない。成熟度の低い組織を説得する武器になる)
- セッションの流れ: 準備 → ブリーフィング → 事前インタビュー(背景・経験)→ モデレーション
  (被験者がタスクを解き**思考発話**。モデレータは静かに観察し、完全に詰まったら次のタスクへ)→
  事後インタビュー(**「良かった点2〜3つ」「改善すべき点2〜3つ」**)
- モデレータは中立で、セッション中に被験者と話せる唯一の人。**アクティブすぎるのは頻出ミス**
  (面接・実演・接待をしない)。観察者(ステークホルダー)こそがテストセッションの主要ユーザー
- 良いタスクの条件: テスト目的に合致 / **被験者にとって意味がある**(ログインやパスワード変更のような
  システム都合のタスクは避け、「商品を注文する」のような文脈のあるものに)/ 中断基準を持つ(例: 10分で打ち切り)
- タスクの並べ方: 最初と最後は簡単に(成功体験で始め、挫折で終わらせない)/ 重要なものを先に /
  被験者にとって論理的な順(注文→キャンセル)/ 前タスクの成功に依存するタスクは避ける
- 場所: ラボ・会議室・被験者の自宅/職場・カフェ(10分以内のクイックテスト向き)。遠隔・非モデレート型もある
- 分析: 記録者がセッション中に観察を記録 → 各セッション直後にモデレータと率直に議論 → 全セッション後、
  **2人が別々に** 問題20〜30件+ポジティブ5〜10件を抽出 → 突き合わせて統合 → 欠陥管理ツールに登録し解決まで追跡。
  70件見つかっても全部報告するのは不可。優先順位づけがモデレータの重要な(不愉快な)仕事
- 結果の性格: テストが示すのは「代表的ユーザーが何を達成できたか」。意見聴取ではない。
  被験者の感想は**過半数が自発的に**述べた場合のみ報告してよい
- 発見の分類: ユーザビリティ問題(重大度必須: 軽微/重大/致命的=被験者が断念/破滅的=身体・重大な金銭被害)/
  ポジティブな発見 / グッドアイデア / 機能欠陥。重大度は頻度×影響×持続性(回避を学習できるか)で判断
- **ポジティブな発見を必ず報告する**(受け入れられやすくなる・直すべきでない箇所が伝わる)
- レポート: 最大25件・最大20ページ・**1ページのエグゼクティブサマリ必須**。専門用語を避け相手の言葉で書く。
  被験者募集の個人情報は載せない。アジャイルでは口頭報告やバックログ直行でも可
- ステークホルダーの巻き込み: 計画・タスク作成・被験者定義・観察に招く。**観察させることが最強の説得**
- 頻出ミス10: 目的不明確 / 実施が遅すぎ / 重大な結果の握りつぶし / 些末な点に集中 / モデレータが喋りすぎ /
  事後インタビュー省略 / ステークホルダー不関与 / 読めないレポート / ポジティブ報告なし / 重大度分類なし

## 第6章 ユーザーアンケート(評価法3)

- 満足度の主観評価を定量化する。手順: 計画 → ユーザー/ステークホルダーへの事前インタビュー(**鮮明な直近の
  経験に焦点**)→ 質問紙選定 → 配布(未回答者に督促)→ 分析 → 報告
- **自作質問より標準質問紙を優先**: SUS(10問・5段階。簡便で最普及)/ SUMI(50問・3択)/ WAMMI(Web向け20問)。
  いずれも過去データとのベンチマーク比較ができ、**完了基準・受け入れ基準の数値として使える**

## 第7章 評価方法の選択(このSkillの対話に最重要)

- 目的で選ぶ: 有効性→テストかレビュー / 効率性の要件充足・改善の測定→定量的テスト / 満足性の要件充足→アンケート /
  組織の意識向上→テスト(懐疑的な相手を説得できる)
- **組織のユーザビリティ成熟度が低いなら、レビューよりテストを選ぶ**(レビュー結果は「ただの意見」と
  却下されやすい)
- 時間: レビューと非モデレート型テストは数日で完了できる
- 段階: プロトタイプしかない初期は形成的な方法(レビュー等)。
  ※原文はここで「formative method such as usability review, quantitative usability evaluation or
  user survey」と記すが、定量的評価=総括的とする1.2節と矛盾する(原文ママ。誤記の可能性が高い)
- リソース不足時の3オプション: **短縮形テスト(被験者3〜5人・モデレータが記録兼任・ラボなし・報告15件程度)** /
  非モデレート型(録画して後で分析。募集が速く安いが分析工数は同じ)/ RITE
- 実利用者を確保できないならテストよりレビュー
- **1プロジェクトで複数の方法を混ぜるのを強く推奨**(例: 先にクイックレビューで重大問題を潰してから
  高価なテストを実施 / カフェで10分×5〜6セッション→後日本格テスト)
- アクセシビリティ評価法の選択基準: 法的要件 / 組織要件 / 対象ユーザー中の障害のある人の数

## 第8章 役割

- ユーザビリティテスター(計画・準備・リスク評価)/ モデレータ(進行・分析・問題の登録と追跡)/
  記録者(発見の記録・分析参加)。兼任可(短縮形ではモデレータが記録も担う)
