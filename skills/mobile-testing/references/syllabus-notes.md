## 1章 Mobile World(ビジネス・技術ドライバ)

- **端末選定はアナリティクスデータ起点**: 地域別のプラットフォーム/OSバージョン/端末タイプ分布、
  画面サイズ・解像度、入力方式を StatCounter 等(無料・商用)から取得し、市場に応じた
  「デバイスポートフォリオ」を組む。選定は**市場カバレッジ×コスト×リスクの妥協点**
- テスト戦略の3アプローチ(端末マトリクス絞りの語彙として使える):
  - **単一プラットフォーム**: 1端末種・1OS版・1キャリア・1ネットワークに限定
  - **複数プラットフォーム**: トラフィック等の分析データに基づく代表選抜(実務の基本形)
  - **最大カバレッジ**: 全組み合わせ=事実上の全数テストで経済的に非現実的
- 端末が手元にない場合の代替: リモートデバイスアクセス(RDA)/クラウドテスト、クラウドソーシング
  (crowd testing)、私的ネットワーク(同僚・知人)、バグハント(ゲーミフィケーションイベント)
- リスク→緩和の対応表: 市場断片化→利用上位端末に絞る / 新技術・新端末の登場→プレプロダクション版で先行確認 /
  端末調達難→RDA・クラウド / 移動中利用のリスク→フィールドテスト
- アプリ種別(ネイティブ/ブラウザベース/ハイブリッド)でテスト内容が変わる。ブラウザベースは
  m-dot・レスポンシブ・アダプティブ・PWA の4形態。ハイブリッドはラッパー起因の性能とlook&feel逸脱が弱点
- ビジネスモデル(freemium/広告/取引課金/有料/エンタープライズ)もテスト観点に影響
  (例: 広告が本質機能を隠していないか)
- 接続アーキテクチャ: never-connected / always-connected / **partially-connected**(オフラインでも
  動き、接続時に同期)。同期は継続 or store-and-forward、同期/非同期転送

## 2章 モバイル固有のテストタイプ(最重量章)

### 2.1 端末ハードウェアとの互換性
- **機能「非搭載」端末での動作もテストする**: 期待機能があれば動くだけでなく、無い場合に
  クラッシュしないこと(例: カメラ2台前提のアプリをカメラ1台/0台の端末で)
- ディスプレイ: 画面サイズ・アスペクト比・密度(dpi/ppi)でのスケーリング、UI要素の重なり、
  高dpiでの画像縮小問題
- 温度: 過熱時のCPUクロック低下・メモリ解放・機能停止がアプリ挙動に波及する
- センサー: GPSのon/off・信号品質・**フォールバック**(Wi-Fi測位・基地局・手入力)、照度、音量、
  各種モーション
- 入力方式: 複数のソフトキーボード(主要メーカー製+普及品)、適切なキーボードの自動表示、
  ジェスチャー(非対応ジェスチャーは無視されること)、カメラ入力
- **画面回転は1回では不十分**: 描画・状態の問題は複数回連続切替で顕在化する。データ保持・
  セッション維持を各画面状態で確認
- 割り込み: 着信・メッセージ・充電開始・低メモリ・通知。**状態/データ/セッションを保持して復帰**
  すること。「おやすみモード」解除直後の通知一斉受信も試す
- 権限: インストール時拒否・後からの取り消しの両方。縮退動作+再要求が丁寧に行われること。
  機能に不要な過剰権限を要求していないこと自体もテスト対象
- 電池: 低電池・電池切れ時の**データ整合性**、フォア/バックグラウンド別の消費。長時間無人実行の
  計画とログ解析ツールが必要

### 2.2 端末ソフトウェアとの相互作用
- 通知: フォア/バック別・低電池下の挙動、通知からの直接操作がアプリ内に反映、ディープリンクは
  ホームでなく該当ページを開く
- クイックアクセス(Androidショートカット/iOS 3D touch): 対応OS版と非対応OS版の両方で正常なこと
- **OSのユーザー設定をアプリが尊重すること**: マナーモードで音を出さない、省電力・日時・言語・
  文字サイズ等の設定変更に追従
- マルチプラットフォーム/OSバージョン間: 後方互換、OSの新機能(例: Android Doze)対応版・
  非対応版の両方でテスト。コード共有がなければ「別アプリを2本テストする」のと同じ
- 他アプリとの共存・相互運用: データ授受の正しさ、相手アプリのデータを壊さない、競合動作
  (一方がGPSを切り、他方が入れる等)。全アプリは無理なのでリスクベースで選ぶ

### 2.3 接続性
- Wi-Fi↔モバイル切替(自宅を出るシナリオ)、セル間移動、圏外(dead spot)、機内モード
- 切替時に予期しない挙動・データ損失がないこと。**制限時はユーザーに理由つきで明示**すること
- 再現手段: エミュレータのネットワーク模擬(限定的)/自前ネットワーク+帯域操作(高コスト)/
  フィールドテスト(安いが再現性が低い)

## 3章 共通テストタイプとテストプロセス

- インストーラビリティ: ストア/サイドロード/デスクトップ経由、OTA/ケーブル。中断・再開、
  「データを残して削除」後の再インストール、更新でデータが消えないこと
- ストレス(端末側限定): 高CPU・メモリ枯渇・ディスク不足・電池・低帯域。Monkey(ADB)等で生成。
  バックエンド側は Performance Testing シラバスの領域
- セキュリティ: 端末内の機微データ、転送・保存の暗号化、異常終了後の一時データ削除、
  パスワード欄のクリア、OWASP Mobile Top 10。詳細は Security シラバスへ
- 性能: **起動が遅い(目安3秒超)と削除される**。主要ワークフローの時間計測(chronometry)を
  競合アプリと比較。体感性能(perceived performance)も対象
- ユーザビリティ: 低品質だと数分でアンインストールされる。**プラットフォームのデザイン
  ガイドライン準拠**が期待値。所見は欠陥ではなく「finding」として説明する立場
- I18N/L10N: 独語・露語などの長い訳語×小画面のレイアウト崩れ、日付形式
- アクセシビリティ: 端末のアクセシビリティ設定ごとに確認。Google/Apple/W3Cのガイドライン参照
- **追加のテストレベル**(通常のレベルに上乗せ):
  - **フィールドテスト**: 実網・実移動での確認。経路・交通手段・時間帯・キャリア契約まで
    事前計画が要る。温度など環境要因も込み
  - **ストア審査テスト**: プラットフォームガイドライン(UI・ライブラリ・API)に基づく
    チェックリストを**提出前に自分で実行**しリジェクトを予防。審査期間と再提出をスケジュールに織り込む
  - **ポストリリーステスト**: 公開後にストアから実際にDL・インストールして確認
- 経験ベース技法: ペルソナ、ニーモニック(SFiDPOT、モバイル特化の **I SLICED UP FUN** =
  Inputs/Store/Location/Interactions&interruptions/Communication/Ergonomics/Data/Usability/
  Platform/Function/User scenarios/Network)、ツアー(Feature/Sabotage/低電池/接続/照度/回転/
  ジェスチャー等)、SBTM(タイムボックス+チャーター+セッションシート)と組み合わせる
- テストアプローチ: モバイルでは**テストピラミッドが逆転しがち**(手動テストが多い)[Knott15]

## 4章 プラットフォーム・ツール・環境

- SDK付属ツール: スクリーンショット・ログ抽出・イベント注入・リソース監視(ADB、AVD Manager、
  iOS Instruments 等)
- **エミュレータ≠シミュレータ**: エミュレータはハードを模擬し**実機と同じバイトコード**を実行。
  シミュレータは実行環境の模擬で専用ビルドが動く(=配布物と別物なのでさらに限定的)
- 使いどころ: 開発初期の高速デプロイ、ネットワーク条件・GPS位置・割り込みの模擬(実機では
  高コストな条件を安く再現)。限界: マルチタッチ・加速度・センサー類・実機固有の挙動差
- テストラボ: **オンプレ**(センサー・電池・NFC/Bluetooth・近接系が試せる。調達維持コスト大)と
  **リモート(クラウド)**(RDA、ロボットアーム、実キャリア回線、海外拠点でのGPS/網テスト。
  応答が遅い・センサー電池系が苦手・常用すると割高)。**併用が前提**

## 5章 テスト実行の自動化

- アプローチ: user-agentベース(ブラウザ偽装。モバイルWeb向け)/デバイスベース(実機上で実行。全種向け)
- オブジェクト認識 vs 画像/OCR比較: 前者は速く画面変更に強いが「ユーザーに見えない要素を操作して
  偽陰性」のリスク。後者はスクリプト不要だが遅くレイアウト変更で全滅
- ツール評価は組織適合+技術適合(FaceID等の新機能対応、ネットワーク条件、大規模並列実行、CI統合)
- ラボ戦略: 初期=オンプレ実機+エミュレータ、後期のフルリグレッション=クラウドの大規模ラボ
  (CI実行では安定性が最重要)。よく整備されたオンプレはリモートに劣らない

   明示する一文を足すと、対話での「絞った根拠」の説得力が上がる
2. **機能非搭載端末のテスト観点**: 「その機能が無い端末で壊れないか」は現SKILL.mdの
   環境条件リストに無く、端末マトリクス選定の対話(両端の意味づけ)を一段深くする
3. **ストア審査チェックリストの提出前自己実行+ポストリリーステスト**: 現状は
   「審査リジェクト→premortem」止まり。ガイドライン準拠テストを提出前に回す予防策と、
   公開後にストアから実DLして確認するレベルの存在は、そのまま対話に使える具体策
