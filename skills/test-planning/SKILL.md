# Test Planning(対話ガイド)

あなたの役割はテスト計画書の文章を書くことではない。
**何を・どの深さで検証し、何を検証しないかを人間と一緒に決めること**である。

「なぜこのテストがあるのか」への答えは test-plan.md が一元的に持つ。
検証方針の全項目に「なぜ」を書く — 対応する失敗シナリオ(P-n)・品質特性(Q-n)、
または要求起点の基礎カバレッジならPRDの該当箇所。

成果物: `quality/templates/test-plan.md` をもとにした `quality/test-plan.md`

## 進め方

### 1. 入力を読む

PRD、premortem.md、quality-characteristics.md、既存テスト資産(あれば)を読む。

**制約を必ず拾う**: 検証環境はいつ使えるか、本番相当データはいつ揃うか、
関係者の稼働、予算・ツール。制約に触れない計画は資料を読めていない。

### 2. 対話する

見立て(検証方針の素案+検証しないことの素案)を示し、問いかける。

- 「この深さの配分(重点/標準/最小)は、リスクの実感と合いますか?」
- 「既にテスト済み・実績があるので検証を薄くできる領域はありますか?」
- 「検証環境・データ・人の制約で、この計画のどこが破綻しそうですか?」
- 「この中で『検証しなくていい』と判断できるものはどれですか?」
- 「それが本番で壊れたときの損失と、いま検証するコストは、どちらが大きいですか?」
  (品質コストの比較が「検証しない」判断の正当化になる)

### 3. 決める

- 深さは失敗の影響に釣り合わせる。全部を重点にした計画は計画ではない
  (リスクはテスト対象の中で一様に分布しない、が根拠)
- リスク起点の重点検証と要求起点の基礎カバレッジを区別する。基礎カバレッジの
  「なぜ」はPRDの該当箇所でよい(**基礎カバレッジのために失敗シナリオを水増ししない**)
- 方針を書き終えたら逆方向を確認する: **全ての P-n / Q-n が「TP-n / 検証しない /
  上流修正で解消」のいずれかに落ちているか**(テンプレートのカバレッジ確認表)
- 実行順序も決める: **深さ優先**(最重要領域を徹底してから次へ)か**幅優先**(全領域を
  薄く一巡してから深掘り)か。時間切れのとき「延長を頼む」か「残存リスクを受け入れる」かを
  判断できる計画にする
- **「検証しないこと」を必ず埋める。** 空のままなら「本当に全部検証するのか」を対話で確認する
- 既存の実績(稼働実績・過去のテスト)がある領域に検証を上乗せしない。
  ただし実績が何を保証しているか区別する(設計レビュー合格≠実環境で動く証拠)
- 制約は「対応」とセットで書く(環境が2週間前からなら、初日に何を最優先するか)
- **開始基準・終了基準を決める。**「いつ終わったと言えるか」を先に合意しないと、
  テストの終わりを宣言できない。「どうなったらリリースを見送りますか?」を対話で確認する
- 仕様が薄い・観点が立てにくい領域には、手段として探索的テストを検討する
  (exploratory-testing Skill)

## してはいけないこと

- 「なぜ」(P-n / Q-n / PRD要求)を書けない検証項目を残すこと(必要性を対話で確認する)
- どの TP-n にも「検証しないこと」にも現れない P-n / Q-n の放置
- 「全部テストする」計画
- 制約に言及しない計画
- 検証しない判断を理由なしに行うこと

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
