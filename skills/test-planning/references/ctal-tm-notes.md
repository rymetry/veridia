## 前提: このシラバスの立ち位置(0章)

- 対象は**プロジェクトレベルのテストマネジメント**。組織レベルのテストマネジメントは
  明示的にスコープ外で、Expert Level(Test Management / Improving the Test Process)へ委譲(0.11)。
- 用語: **テスト戦略**=目的達成のためのテストのやり方の記述。**テストアプローチ**=
  テストレベル・テストタイプ・技法の選択と組み合わせという実装方法。アプローチの選択が
  戦略策定の中心的な意思決定(0.11)。
- 組織テスト戦略は「所与」として扱う。存在しない/不足する場合はステークホルダーと
  対話して埋める(1.4 導入)。→ Veridiaが組織テストポリシーを持たない前提と整合する。

## 1章 Managing the Test Activities(test-planningに最も効く章)

### 1.1 テストプロセス(計画・監視コントロール・完了)

- テスト計画のタスク: コンテキスト理解 → プロダクトリスクの識別・分析 → リスク対応方針の
  選択 → テストアプローチ定義とリソース見積り・割当 → **全ステークホルダーが合意した計画の確立**。
  意見の不一致は解消してから計画とする。
- 計画は反復的。プロジェクト進行に応じて再計画する(要求確定前から始めてよい)。
- テストコントロールの要点: 逸脱の管理、**新規・変化したリスクの扱い**、開始準備の確立、
  **終了基準に基づくテスト完了の承認**。
- テスト完了(1.1.3): 完了報告の作成と承認 / テストウェアのアーカイブと引き継ぎ
  (受容・繰延した既知欠陥の伝達を含む)/ 未解決欠陥は変更要求やバックログ項目に変換 /
  環境の復元 / **教訓の記録(レトロスペクティブ)**。

### 1.2 テストのコンテキスト

- ステークホルダー分析(power-interest マトリクス: Promoters/Latents/Defenders/Apathetics)を
  戦略・計画作成の一部として行う。リスク識別の参加者選定にも直結。
- SDLCモデル・テストレベル・テストタイプごとのマネジメント活動の違いを整理
  (シーケンシャル=事前の詳細見積り・文書中心、Agile=イテレーション内・最小文書)。
- ハイブリッド開発(移行目的 or 適材適所)の運営上の留意点。

### 1.3 リスクベースドテスト(深さ配分の理論的裏付け)

- **リスクレベルが高いほど、テストを早く始め、より厳密に、より長く行う**。逆に低リスクは
  遅く・軽くてよい。→ Veridiaの「重点/標準/最小」の深さ配分そのもの。
- **リスクはテスト対象内で一様に分布しない**。同一対象でも部位ごとにリスクが違うため、
  一様な厳密さでテストする必要はない(1.3.2, 1.3.4)。→「全部を重点にした計画は計画ではない」の裏付け。
- リスクレベル = 発生可能性 × 影響。可能性の要因例: 技術の複雑さ、スキル・稼働の問題、
  変更頻度の高さ、早期QA活動の欠如。影響の要因例: 利用頻度、機能の重要度、評判毀損、
  金銭的・法的損失、**合理的な回避策の欠如**。データが乏しければ定性的な順序尺度でよい。
- 緩和策はテストだけではない: 回避策の用意(コンティンジェンシー)、第三者へのリスク移転、
  **リスク受容**も選択肢(1.3.4)。→「検証しないこと」はリスク受容の明文化と読める。
- 実行順序の2戦略(1.3.4): **深さ優先**(高リスクから降順。最高リスクの早期緩和を優先)と
  **幅優先**(全リスクを最低1件ずつ先にカバーし、品質の全体像を早く得る)。実務では
  深さ優先で始め、時間が逼迫したら幅優先に切り替えることが多い。
- **時間切れで計画分を消化できないとき、リスクベースドテストは「テストを延長するか、
  残存リスクを受容するか」の判断材料を経営層に提供できる**。残存リスクの水準で進捗を
  報告すれば、リリース判断をリスクで語れる(1.3.4)。
- 技法は重量級(FMEA、ハザード分析、費用暴露、フォルトツリー。セーフティクリティカル向け)と
  軽量級(PRAM、PRISMA、SST。ステークホルダー入力だけでも機能する)がある。非安全系は
  通常軽量級で足りる。→ Veridiaのプレモーテムは軽量級の系譜として妥当。
- 成功の振り返り指標(1.3.6): 適切なステークホルダーが参加したか / 高優先欠陥が実行初期に
  出たか / **結果をリスクの言葉で説明できたか** / スキップしたテストのリスクは実行分より低かったか。
- 落とし穴(1.3.6): リスク水準の見積り困難(履歴データと関係者評価で補う)/ 短期圧力での
  形骸化 / **毎回同じリスクが挙がる「déjà vu」による慢心** / 不適切な人選による重要リスクの
  見落とし / **ステークホルダーとリスクは変わるので、リスク分析は一度きりでなく反復活動**。

### 1.4 プロジェクトテスト戦略

- アプローチ選択の分析要因: ドメイン(規制で厳密さ・文書量が変わる)、組織・プロジェクトの
  目標、**テストリソースの制約(ツール・環境・要員・スキル)**、SDLC、他システムとの
  インターフェース、**テストデータの入手制約(匿名化・本番相当データ等)**。
  → SKILL.md の「制約を必ず拾う」と同じ趣旨。環境・データ・人はシラバスでも一級の入力。
- **テスト目的と終了基準は S.M.A.R.T. で定義する**(1.4.3): 具体的・**測定可能**・達成可能・
  関連性・**期限付き**。数えられない目的は終了判定に使えない。
- 環境が複数必要で同時には使えない場合があることを、達成可能な目的・終了基準の設定時に
  織り込む(1.4.3)。→ 制約と終了基準を連動させる根拠。
- 文書化の要否はコンテキスト次第。正式なテスト計画書の形は必須ではないが、契約・規制が
  あれば要求される(1.4 導入)。

### 1.5 テストプロセス改善 / 1.6 テストツール(概要のみ)

- 改善は IDEAL モデル。モデルベース(TMMi、TPI NEXT)と分析ベース(根本原因分析、GQM)がある。
- **レトロスペクティブ**(1.5.4): 導入 → データ収集(定性+定量)→ 改善案導出 →
  アクション決定(一度に多くやらない)→ 振り返り自体の見直し。両開発モデルで有効。
- ツール導入はROI・ライフサイクル(取得/保守/進化/退役)・パイロット等の組織的活動(1.6)。

## 2章 Managing the Product

### 2.1 テストメトリクス

- メトリクスは**テスト計画時に、テスト目的と対応づけて定義する**。監視・コントロール用
  (進捗)と完了判定用(目的達成)は区別する。例: 要求カバレッジ・**プロダクトリスク
  カバレッジ**は両方、コードカバレッジ・コストは監視用。
- リスク関連の報告例: 全テスト合格のリスク% / 一部失敗のリスク% / 未テストのリスク%。
- **欠陥検出が減衰してきたら、メトリクスの報告と合意済み終了基準に基づいてテスト終了を
  判断する**(2.1.3)。→ test-cases の完了判定はこの構図。
- 上位レベルのテストでは構造カバレッジより要求・リスクベースの報告が適切。100%の
  構造カバレッジでも上位レベルで扱うべきリスクは残る。

### 2.2 テスト見積り

- 工数・期間・コストの見積り技法(メトリクスベース/エキスパートベース、三点見積り、
  Wideband Delphi、プランニングポーカー)の選択論。**見積りの前提は必ず文書化し、情報が
  変われば更新する**。
- 工数に影響する要因: テストベースの品質、プロダクトの規模・複雑さ、開発プロセスの成熟度、
  **人(スキル・稼働・満足度)**、過去の欠陥実績、チームの分散。

### 2.3 欠陥マネジメント

- 欠陥ワークフロー(OPEN → IN PROGRESS → REJECTED/RESOLVED → CLOSED)の設計原則:
  終端状態は1つ、連続する状態は異なる役割が持つ、**入力必須属性は価値あるものに限定**。
- トリアージ(欠陥マネジメント委員会)は修正の便益・リスク・コストで判断する。
- Agileでは軽量でよいが、**欠陥票を作る条件を予め決めて文書化する**(ブロッカー、同一
  イテレーション内で解決できないもの、他チーム・サプライヤー起因等)。
- 欠陥データは工程封じ込め・根本原因・クラスタ分析を通じて改善の入力になる。**欠陥を
  記録しない運用は効率の名の下に行われがちだが、プロセスの可視性を大きく損なう**(2.3.6)。

## 3章 Managing the Team

- 3.1 テストチーム: 4つのコンピテンス(専門・方法・社会・個人)、スキルマトリクスによる
  ギャップ分析、育成手段、Tuckmanモデル、Herzbergの動機づけ・衛生要因。
- 3.2 ステークホルダー関係: **品質コスト**の4分類 = 予防コスト / 評価(テスト)コスト /
  内部失敗コスト / 外部失敗コスト。通常、評価+内部失敗コストは外部失敗コストより
  はるかに小さい(=テストの価値の根拠)。
- **過剰なテストは便益を上回る遅延とコストを生み、過少なテストは低品質を出荷する。最適は
  その間にある**(3.2 導入)。テスト工数はプロジェクト・プロダクトのリスクと、事業が取れる
  リスクに基づかせる。→「検証しないこと」を費用対効果で語る直接の根拠。
- 既知欠陥を抱えたままのリリースが待つより良い場合もある。可否は発生確率と重大度に依存(3.2.2)。

## 「対象外」判断の検証結果

### 除外が妥当な部分(Veridiaの判断を本文が支持)

- **組織レベルのテストポリシー・組織テスト戦略**: シラバス自身がプロジェクトレベルに限定し、
  組織レベルはExpert Levelへ委譲(0.11)。組織戦略は「所与、なければ対話で埋める」であり、
  対話ハーネスのVeridiaはまさに後者を実践している。除外は妥当。
- **チーム管理(3.1)**: 採用・スキル評価・育成・動機づけは人事・ラインの領域で、
  成果物駆動のVeridiaに載せる意味が薄い。除外は妥当。
- **見積り技法の詳細(2.2.3)**: Wideband Delphi等の工数見積りはプロジェクト管理の道具で、
  Veridiaは工数計画を成果物にしない。除外は妥当。ただし2.2.2の「工数に影響する要因」は
  制約の対話の語彙として一部流用可(下記)。
- **テストプロセス改善モデル(TMMi/TPI NEXT)とツール選定ROI(1.5.2, 1.6)**: 組織的・
  長期投資の話。除外は妥当(改善はレトロスペクティブだけ拾えば足りる)。
- **欠陥マネジメント委員会・専任ディフェクトマネージャー(2.3.2)**: 大規模組織向け。除外は妥当。

### 実は軽量ハーネスにも効く部分(除外し過ぎに注意)

- **リスクベースドテストの実行順序と残存リスク報告(1.3.4)**: 深さ優先/幅優先、
  「時間切れ時に延長かリスク受容かを判断できる形にする」は、深さ配分を決めた後の
  実行計画・完了判定の対話にそのまま効く。現SKILL.mdには無い観点。
- **S.M.A.R.T.な終了基準(1.4.3)**: テンプレートの終了基準例は既に測定可能だが、
  規律として明文化されていない。「測定できない終了基準は判定できない」は昇格価値あり。
- **品質コストによる「検証しないこと」の正当化(3.2)**: 現テンプレートの理由欄は自由記述。
  「外部失敗コスト見合いで判断する」という問いを足すと理由の質が上がる。
- **リスク分析は反復活動・déjà vu への警戒(1.3.6)**: 再レビュー時に「検討したが外したもの」を
  先に読む現運用は、同じ議論の防止と同時に慢心(毎回同じリスクで満足する)の温床にもなる。
  「前回と何が変わったか」を問う一手が要る。
- **テスト完了時の教訓記録と未解決欠陥のバックログ化(1.1.3)**: test-cases の完了判定に
  「残欠陥の行き先」と「教訓」を残す観点。
- **Agileの欠陥票作成条件の事前合意(2.3.3)**: 軽量運用でも「どこから票にするか」だけは
  決めて文書化せよ、は小規模プロジェクトにこそ効く。

## 昇格候補(最大5件)

**反映状況(2026-08-16)**: 全5件反映済み(1 skills/test-planning「決める」+templates/test-plan
「実行の方針」節 / 2 templates/test-plan 終了基準 / 3 skills/test-planning 対話 /
4 operating-model 再レビュー節 / 5 templates/test-cases 完了判定)

1. **skills/test-planning/SKILL.md**: 「決める」に実行順序の観点を追加 —
   重点領域は深さ優先で先に潰し、時間逼迫時は幅優先へ切替。時間切れ時に
   「延長か残存リスク受容か」を判断できる形で計画する(1.3.4)。
2. **templates/test-plan.md**: 終了基準の節に「基準は測定可能・期限付き
   (S.M.A.R.T.)で書く。測定できない基準は終了を判定できない」の一文を追加(1.4.3)。
3. **skills/test-planning/SKILL.md**: 「検証しないこと」の対話の問いに
   「この領域で失敗が漏れたときの外部失敗コストは、検証コストと見合うか」を追加(3.2)。
   リスク受容・回避策・第三者移転という緩和の選択肢も提示できるとよい(1.3.4)。
4. **skills/test-planning/SKILL.md**(再レビュー関連の一文)または docs/operating-model.md:
   再レビュー時は「検討したが外したもの」の再確認に加えて「前回から変わった前提・
   ステークホルダー・新リスク」を必ず問う(1.3.6 déjà vu / stakeholder churn)。
5. **skills/test-cases/SKILL.md または templates/test-cases.md**: 完了判定に
   「未解決欠陥の行き先(バックログ化・受容の明記)」と「教訓の記録先」を含める(1.1.3, 2.3.6)。
