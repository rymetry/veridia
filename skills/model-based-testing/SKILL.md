# Model-Based Testing(対話ガイド)

あなたの役割はモデリングツールの導入ではない。
**複雑な振る舞いをモデルに起こし、「どこまで網羅すれば十分か」を
根拠をもって決めること**である。

新しい成果物は作らない。モデルは test-design.md に含める(Mermaid等のテキスト図で)。

## いつ使うか

- 状態遷移が絡む機能(貸出中→返却→再貸出、承認フロー、契約ステータス)
- 業務ルールの分岐が多い機能(料金計算、権限判定)
- 「ケースが漏れていそうで不安」というとき(モデルは漏れを可視化する道具)

## 進め方

### 1. モデル化する価値がある箇所を選ぶ

- 全機能をモデル化しない。**状態・分岐の複雑さが痛い場所だけ**
- 「この機能、状態は何個ありますか? 紙に描けますか?」— 描けないなら価値がある

### 2. モデルを対話で作る

- 状態遷移: 状態と遷移を列挙 → **仕様にない遷移(モデルの空白)こそ聞く**
  「返却処理中にキャンセルされたら? この遷移は起きないと言えますか?」
- デシジョンテーブル: 条件を列挙して全組み合わせを出す → ありえない組を潰す
- モデル化の過程で見つかる仕様の穴は、そのまま上流へのフィードバックになる。
  **モデルの最大の価値はケース生成ではなく、この穴の発見である**

### 3. 網羅基準を決めて絞る

モデルができたら「どこまでやるか」を決める。

```text
状態遷移     全状態 / 全遷移 / 遷移の組(1-switch)…
テーブル     全列 / 有効な列のみ
```

- 基準はリスク(test-plan の深さ)と釣り合わせる。重点なら全遷移、標準なら主要経路
- 選んだ基準と理由を test-design.md の絞り方に記録する

### 4. 書き込む先

| 内容 | 書き先 |
|---|---|
| モデル(テキスト図)+網羅基準と理由 | test-design.md |
| モデルから導いたケース | test-cases.md |
| モデル化で見つかった仕様の穴 | 上流へのフィードバック |
| モデルにない遷移が「起きない」根拠が不明なもの | premortem.md へ提案 |

## してはいけないこと

- モデルの精緻化を目的にすること(発見と網羅根拠のための道具)
- 1つのモデルでテスト対象の全てを表そうとすること(目的別に小さいモデルを複数作る)
- 網羅基準を決めずにモデルから全ケースを生成すること(爆発する)
- モデルと実装が乖離したまま放置すること(仕様変更時はモデルも更新。
  何が変わったらどれを直すかは references/syllabus-notes.md の影響マップを参照)

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
