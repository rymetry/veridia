## 1章: MBTの導入

- MBTは伝統的技法(同値分割・境界値・デシジョンテーブル・状態遷移)の置き換えではなく拡張
- 効果は2軸: 有効性(モデル化がステークホルダーとの対話を促し、要件の誤解を早期発見。
  システムが存在する前にテストを分析できる)と効率(単一保守点、再利用、自動生成)
- **誤解と落とし穴**(このSkillの「してはいけないこと」の裏付け):
  - 「MBTが全部解決する」— 既存技法を誤用するチームはMBTでも失敗する
  - 「ツールの問題だ」— ツール購入を先にしない。測定可能な改善目標の定義が先
  - 「モデルは常に正しい」— モデルにも欠陥は入る。レビュー・静的解析・シミュレーションで
    検証必須。モデルの変更は生成物全体に波及するため変更前レビューが必要
  - 「ケース爆発は不可避」— 選択基準とフィルタで制御できる(3章)
- 主に高位テストレベル(システム/受入)の機能テストで使う。要件工学支援
  (要件の欠落・不整合の早期発見、双方向トレーサビリティ自動化)が大きな価値

## 2章: MBTモデリング

- **モデリングの3つの問い**: (1)何の品質特性をモデル化するか (2)どの言語が適切か
  (3)抽象度はどこか。抽象的なほど理解しやすいが、実行時のアダプテーションが重くなる。
  抽象度は「誰とそのモデルで議論したいか」も決める
- **モデルの3つの主題**(使い分けの語彙):
  - システムモデル: あるべき姿。生成テストは「実装がモデルに従うか」を検証
  - 環境/利用モデル: 利用者の振る舞い(例: マルコフ連鎖)。想定利用への適合の確信を得る
  - テストモデル: テストケース自体のモデル(手順のグラフ表現など)
- **目的→モデルの対応例**: 業務フロー検証→業務プロセス図/活動図、状態依存の応答検証→
  状態遷移図、業務ルール→デシジョンテーブル、利用適合→利用モデル
- **モデル品質の3特性**: 構文的(記法に正しい)/意味的(内容が正しい)/語用的
  (テスト目的に適う)。ツールは構文まで、レビューが意味・語用を担う
- **初心者の典型ミス**: 詳細の入れすぎ・省きすぎ(目的に対する抽象度の誤り)、
  1つのモデルで全部を表そうとする。**目的別に複数の小さいモデルに分けるのが正**
  (例: 実装検証は状態遷移図、フロー妥当性確認は活動図)
- 要件をモデル要素にリンクすると: レビュー容易化、要件カバレッジ測定、要件優先度による
  テスト選択、変更影響分析(回帰範囲の決定)が可能になる。リスク・優先度・所要時間等の
  付加情報もモデルに載せられる
- **既存モデルの再利用は要注意**: 設計モデルの流用は単一ソース問題(設計の誤りがテストにも
  伝播し、独立性を失う)。流用のみでは検証(仕様通りか)しかできず妥当性確認にならない。
  テスター視点で「仕様にない遷移」等を追加して初めてMBTモデルになる
- モデルは反復開発する。要素を足すたびにテスト生成して確かめる(生成=モデルのシミュレーション)

## 3章: テスト選択基準(このSkillの中核)

- 同じモデルから複数のテストスイートが作れる。選択基準が「意味のある部分集合」を決める
- **6ファミリー**: (1)要件カバレッジ (2)モデル要素カバレッジ (3)データ関連
  (同値分割・境界値・n-wise) (4)ランダム/確率的 (5)シナリオ/パターンベース
  (6)プロジェクト駆動(リスク・優先度・必要設備などの付加情報で選ぶ)
- **モデル別のカバレッジ基準の具体例**:
  - 活動図/業務プロセス図: 活動網羅 / 分岐(ゲートウェイ)網羅 / パス網羅(ループ有無)
  - 状態遷移図: 状態網羅 / 遷移網羅 / 遷移ペア網羅(連続2遷移=1-switch) / パス網羅
  - デシジョンテーブル: 全条件・全決定 / 全アクション
  - データ: 同値クラス代表1つ / 境界値
- **各基準の長短**(基準選定の対話でそのまま使える):
  - 要件カバレッジ: (+)規制で必須のことが多い (-)「1要件複数振る舞い」時の達成定義が曖昧
  - モデルカバレッジ: (+)未カバー箇所が見える (-)パス網羅系は爆発する
  - データ関連: (+)同値分割は事実上必須 (-)組み合わせが重い
  - ランダム: (+)予期しないケースを拾う (-)業務的に無意味な長いテストが出る
  - シナリオ/パターン: (+)回帰テスト向け (-)シナリオの定義・保守コスト
  - プロジェクト駆動: (+)テスト管理に有用 (-)情報をモデルに紐づける手間
- **実務では基準を組み合わせる**: 積(全基準を満たすものだけ=絞る)と和(いずれかを
  満たすもの全部=広げる)。例: 要件カバレッジ×モデルカバレッジ、シナリオ×データ関連
- 選択は再現可能でなければならない。**選んだ基準と理由を文書化する**(Skillの
  「基準と理由を test-design.md に記録」の直接の裏付け)
- モデルの小さな変更で選択結果が全く変わりうる。「モデルがマスター、ケースは派生物」
- 選択基準こそがケース爆発への対抗手段。生成の自動化度は手動/半自動/全自動の3段階
  (手動導出も成立するが効率の利点は薄い)

## 4章: テスト実装と実行

- 高位ケース(具体値なし、業務アナリストのレビュー向け)と低位ケース(具体値・詳細手順、
  実行向け)。高位→低位には具体的アクション・入力値・期待値の補完が必要
  (モデル内に持つか、抽象値⇔具体値の対応表を外に持つ)
- 実行は手動/自動。自動はオフライン(先に全スクリプト生成後に実行)とオンライン
  (on-the-fly: 1ステップずつ生成と実行を交互に。実行結果が経路選択に影響)
- **テストアダプテーション層**: モデルの抽象と実インターフェースの橋渡し(キーワード駆動の
  ラッパーに相当)。UI変更が機能に影響しない場合はこの層だけ直せばよい、という保守の要
- **変更の影響マップ**(保守の対話に使える):
  - 要件・テスト対象の変更 → モデル+選択基準+アダプテーション層
  - インターフェースのみの変更(機能不変) → アダプテーション層のみ
  - テスト目的の変更 → モデル+選択基準+アダプテーション層
- 変更管理は影響分析→選択肢検討→適用→レビューのプロセスで行う
- スクリプト連鎖には前提条件の保証が必要(各スクリプト冒頭でセットアップするか、
  前のスクリプトの事後条件を使う)

## 5章: MBT導入の評価と展開

- 導入は認知→関心→評価→試行(KPI定義+パイロット)→採用の順。ROI見積りとKPIが前提
- 節約要因: 早期の要件検証(後工程の修正費回避)、冗長性のないテスト設計
  (モデルは全パスを重複なく1つの成果物に持つ)、生成自動化による保守削減、
  系統的な選択によるケース数削減
- KPI例: モデルにトレースされた要件数と要件カバレッジ率、モデル規模・複雑度、
  **モデリング中に見つけた要件欠陥数**、モデル再利用率、生産性/欠陥検出の改善率
- 組織目標との対応: 品質向上なら開発と独立したテスト用モデル+明確な抽象度、
  工数削減なら自動化+再利用、コミュニケーション改善なら相手に合う抽象度。
  目標が矛盾する場合は目的別に別モデルを作って解決
- コスト: 初期(ツール評価・ガイドライン整備・訓練・初期モデル・資産移行)と
  経常(モデルのリファクタリングと検証、選択基準の選定、アダプテーション層開発、
  モデル品質の継続チェック)。**モデル保守は経常コストとして計画に入れる**
- モデリングガイドラインがないプロジェクトは典型ミスを犯しやすい(追加リスク)
- ツールは構成管理・要件管理・テスト管理・自動実行と統合してこそ機能。CI統合
  (回帰テストの自動生成・実行)も推奨

## 付録A(K3試験用の簡易言語)

- 活動図サブセット: 開始/終了・アクション・判断/合流・フロー(ガード式)・並行(fork/join)・
  要件リンク(破線)・サブ図。状態機械サブセット: 状態・遷移注釈「event [condition] / action」・
  要件リンク・サブ図。「単純」の定義は15要素未満 — モデルの粒度の目安になる
