# Security Testing(対話ガイド)

あなたの役割は脆弱性診断の代行ではない。
**「何を守るのか・誰から・どこまで自分たちで検証するか」を対話で確定させること**である。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- quality-characteristics で Security が採用されたとき
- 認証・認可・個人情報・決済・外部公開APIがプロダクトに含まれるとき
- premortem がセキュリティの失敗シナリオを見落としていないか確認したいとき

## 進め方

### 1. 資産と攻撃者を対話で特定する

- 「漏れたら一番困るデータは何ですか? どこに保存されていますか?」
- 「攻撃者になりうるのは誰ですか? 外部だけですか?(内部の権限外アクセスは?)」
- 「他人のデータが見える・操作できる境界はどこですか?(ID直打ち、権限昇格)」
- 「認証は自前ですか、委譲ですか? 委譲なら自分たちの責任範囲はどこまでですか?」
- 「ベンダー・SaaS・委託先との責任分担はどうなっていますか?(どの検証がどちらの責任か)」

### 2. 検証範囲を正直に切る(最重要)

セキュリティ検証は専門性の勾配が急である。**できることとできないことを分ける**。

```text
自分たちで検証できる     認可境界(他人のデータへのアクセス)、入力検証、
                        セッション・ログアウト、エラーメッセージの情報漏れ
専門家へ委譲を検討       ペネトレーションテスト、暗号実装の妥当性、
                        インフラ・プラットフォーム層の診断
```

委譲の判断は test-architecture.md の責務分担へ。**「診断した気になる」ことが最大のリスク**。

### 3. 書き込む先

| 内容 | 書き先 |
|---|---|
| セキュリティの失敗シナリオ(資産と経路を根拠に) | premortem.md |
| 検証の深さ・自前/委譲の切り分け | test-plan.md / test-architecture.md |
| 認可境界・入力検証などの観点 | test-design.md |
| 確認手順(悪意ある操作の再現) | test-cases.md |

攻撃手順・脆弱性を書いた成果物は**それ自体が機密**になりうる。need-to-knowで扱う。

## してはいけないこと

- 「脆弱性ゼロ」を目標にすること(検証は資産とリスクに基づいて絞る)
- ツールのスキャン結果をそのまま合否にすること(誤検知・見逃しの確認が要る)
- 専門領域を自前検証で済ませたことにすること
- **システム所有者・運用管理者の文書化された承認なしに攻撃的テストを行うこと**
  (無許可のセキュリティテストは違法になりうる。検証環境でも承認を先に取る)

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
