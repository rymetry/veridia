# Test Cases(対話ガイド)

あなたの役割はケースの大量生成ではない。
**観点(TD-n)を、実行する人が迷わない粒度のケースへ、人間と一緒に落とすこと**である。

成果物: `templates/test-cases.md` をもとにした test-cases.md(表形式)

## 進め方

### 1. 入力を読む

test-design.md を読む。観点(TD-n)と判定方法(明確/人の判断)が展開の単位になる。

### 2. 振り分ける

- 判定方法が「明確」な観点 → テストケース表へ
- 判定方法が「人の判断」の観点 → 確認会・レビュー表へ。**無理にケース化しない**

### 3. ケースへ落とす

- test-design.md の「パラメーターと値候補」の絞り方に従ってケースを列挙する。
  **絞り方に書かれていない組み合わせを勝手に増やさない**(必要だと思ったら
  test-design.md 側の絞り方を対話で更新してから)
- 1観点=1ケースとは限らないが、**数を増やすことを目的にしない**。
  同じ失敗を防がない複製ケースは作らない
- 手順は実行する人が迷わない粒度で書く。長い場合は `<br>` で改行し、
  表に収まらない前提・データは表の下に補足として書く
- 期待結果は手順に対して具体的に書く(「正常に動作する」は期待結果ではない)
- 曖昧語を避け、1ケース1目的で小さく作る(大きなケースは失敗時の切り分けを壊す)
- **実施列は必ず「未」で作る。** ケースを書いたことと検証したことを混同しない

対話の例:

- 「この手順、実際に実行するのは誰ですか? その人はこの記述で迷いませんか?」
- 「このデータ(アカウント・環境)は誰がいつ用意しますか?」
- 「実施済みにできる既存の確認(過去のテスト・稼働実績)はありますか?」

### 4. 実行順序に束ねる

ケースが揃ったら、実行しやすいまとまり(スイート)と順序を決める。

- 前提条件を満たす順か(ログイン前に購入のテストをしない)
- 同じ準備データ・環境でまとめられるか
- 重要なケースを先に実行できるか(制約で実施時期が固定のものはそれに従う)

対話の例:

- 「最初にNGが出たら一番困るのはどのケースですか? それを先頭にできますか?」
- 「この並びで実行したとき、環境の初期化は何回必要ですか?」

### 5. 実施時

- 実施したら実施列と結果・証跡列を更新する。証跡(スクリーンショット・ログ)への
  リンクを残す
- NGのケースは課題を起票して結果列にリンクを書く。起票には再現手順・
  期待/実際・環境/データ・証跡を含める(テンプレートの記録項目を参照)
- **NGのケースを通すために期待結果の方を変えない** — 期待結果が誤っていた
  場合は、その根拠(PRD・設計のどこが正か)を人間と確認してから直す
- 修正後は「直ったことの確認(同一手順の再実施)」と「影響範囲のスイート再実行」を
  セットで行う

### 6. 完了判定

- test-plan.md の終了基準に照らして判定する。**実施率の報告ではなく基準への
  合否を出す**
- 満たさない基準は、扱い(受容 / 延期)を人間の判断として記録する。
  「どうしますか?」ではなく「この残NGを受容してリリースする判断をしますか?」と
  具体で問う

## してはいけないこと

- 対応する TD-n のないケースの量産
- 「人の判断」の観点の無理なケース化
- 実施していないケースを実施済みにすること
- 「ケースが書けた」を「検証できた」として報告すること

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
