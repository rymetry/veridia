# Test Cases(対話ガイド)

あなたの役割はケースの大量生成ではない。
**観点(TD-n)を、実行する人が迷わない粒度のケースへ、人間と一緒に落とすこと**である。

成果物: `templates/test-cases.md` をもとにした test-cases.md(表形式)

## 進め方

### 1. 入力を読む

test-design.md を読む。観点(TD-n)と判定方法(明確/人の判断)が展開の単位になる。

### 2. 振り分ける

- 判定方法が「明確」な観点 → テストケース表へ
- 判定方法が「人の判断」の観点 → 確認会・レビュー表へ。**無理にケース化しない**

### 3. ケースへ落とす

- 1観点=1ケースとは限らないが、**数を増やすことを目的にしない**。
  同じ失敗を防がない複製ケースは作らない
- 手順は実行する人が迷わない粒度で書く。長い場合は `<br>` で改行し、
  表に収まらない前提・データは表の下に補足として書く
- 期待結果は手順に対して具体的に書く(「正常に動作する」は期待結果ではない)
- **実施列は必ず「未」で作る。** ケースを書いたことと検証したことを混同しない

対話の例:

- 「この手順、実際に実行するのは誰ですか? その人はこの記述で迷いませんか?」
- 「このデータ(アカウント・環境)は誰がいつ用意しますか?」
- 「実施済みにできる既存の確認(過去のテスト・稼働実績)はありますか?」

### 4. 実施時

- 実施したら実施列と結果・証跡列を更新する。証跡(スクリーンショット・ログ)への
  リンクを残す
- NGのケースは結果列に課題へのリンクを書く。**NGのケースを通すために
  期待結果の方を変えない** — 期待結果が誤っていた場合は、その根拠
  (PRD・設計のどこが正か)を人間と確認してから直す

## してはいけないこと

- 対応する TD-n のないケースの量産
- 「人の判断」の観点の無理なケース化
- 実施していないケースを実施済みにすること
- 「ケースが書けた」を「検証できた」として報告すること
