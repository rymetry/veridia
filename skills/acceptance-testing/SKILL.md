# Acceptance Testing(対話ガイド)

あなたの役割は受け入れテストを代行することではない。
**「誰の・何の合格をもって受け入れとするか」を早期に確定させ、
業務の言葉で検証できる形にすること**である。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- 業務部門・発注者による受け入れ判定があるプロダクト
- 確認会(test-cases.md のR表)の中身を設計するとき
- 受け入れ基準が曖昧なままリリースが近づいているとき

## 進め方

### 1. 受け入れ基準を共同で書く(実装より前に)

- 「『使える』と判定するのは誰ですか? その人は何を見て判定しますか?」
- 「業務が回ると言えるための最低限のシナリオは何ですか?(例外も含めて)」
- 「受け入れで初めて要求の誤解が発覚するのが最悪の展開です。
   基準を今、業務の言葉で書けますか?」

基準は Given/When/Then 調でなくてよい。**業務の人が読んで合否を言える文**にする。

### 2. 業務プロセスで観点を出す

機能単位ではなく業務の流れ(開始→分岐→例外→完了)でシナリオを作る。

- 業務ルールの分岐(承認条件、金額の閾値、権限)を表に起こして網羅を確認する
- 繁忙期・月末・年度替わりなど**業務カレンダー由来の状況**を含める
- 網羅の水準を業務側と事前合意する(例: 主要シナリオは全経路、代替フローは各1経路。
  受け入れ=全機能の再テスト、を防ぐ具体策)
- 非機能の受け入れ(この人数で使える・この時間内に終わる)も基準に含める

### 3. 書き込む先

| 内容 | 書き先 |
|---|---|
| 受け入れ観点での失敗シナリオ(業務が回らない形) | premortem.md |
| 受け入れの体制・時期・参加者の確保(制約になりやすい) | test-plan.md |
| 業務シナリオ・業務ルールの観点 | test-design.md |
| 受け入れ確認会の設計(参加者・シナリオ・記録) | test-cases.md のR表 |
| 受け入れ基準の曖昧さ・矛盾 | 各成果物の上流へのフィードバック |

### 4. 実施の設計

- 業務担当者の時間は貴重。**シナリオ・データ・環境は開発側で全て準備**し、
  当日は判定に集中してもらう
- スクリプト通りの確認だけでなく、業務担当者による探索
  (exploratory-testing Skill)を1セッション組み込むと、実運用との乖離が出やすい
- 確認会の出口は3択で事前合意する: **そのまま受け入れ / 留保付き受け入れ
  (回避策の周知・対象機能の除外)/ 差し戻し**
- 不合格が出たら、技術側が事象と再現条件を特定し、**業務影響と優先度の判定は業務側**が行う(役割を分ける)

## してはいけないこと

- 受け入れ基準の作成をリリース直前まで先送りすること
- 開発側の言葉(API・テーブル名)で受け入れ基準を書くこと
- 受け入れ=全機能の再テストにすること(業務が回るかに絞る)
- 業務担当者の「なんか違う」を却下すること(要求の誤解のシグナルとして扱う)
