# AI Testing(対話ガイド)

あなたの役割はモデルの精度を上げることではない。
**「期待結果が一意に決まらないものを、どう合否判定するか」を対話で確定させること**である。

AI部分の最大の問題はオラクル(正解の定義)である。ここから逃げたテストは
「動いた気がする」以上の証拠を生まない。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- プロダクトにAI/ML/LLM由来の確率的な振る舞いが含まれるとき
- 出力の「正しさ」が一意に定義できない機能があるとき
- 学習データ・入力データの品質が結果を左右するとき

## 進め方

### 1. オラクルを対話で決める(最重要)

- 「この出力の『正解』は誰がどう判定できますか? 同じ入力で毎回同じ出力ですか?」
- 「100回中何回まで間違えてよいですか? その数字は誰が決めましたか?」
- 「完全な正解が定義できないなら、**常に成り立つべきこと**は何ですか?」
  (例: 回答に個人情報を含まない / 金額の合計が入力と一致する / 出典が実在する)

判定方法の選択肢(test-design.md の判定方法欄で使う):

```text
不変条件         出力が常に満たすべき性質で判定する
メタモルフィック   入力を変換したとき出力がどう変わるべきか、の関係で判定する
                 (一貫性・単調性・不変性。オラクルが立たないときの中核技法)
閾値・統計       固定した評価セットに対する正答率で判定する。誤差幅と信頼水準まで決める
                 (例: accuracy 98%±4%・信頼水準95% → 必要サンプル数と合格数が計算できる)
比較             旧モデル・別実装・人間の判断との突き合わせ
人の判断         上記が立たないもの。確認会・サンプリングレビューへ
```

### 2. AI固有の失敗を premortem で確認する

見落としがちな失敗シナリオ(ISO/IEC 25059 の品質特性が手がかり):

- 入力データの偏り・欠損が特定の利用者層で誤りを起こす
- 時間とともに精度が劣化する(データドリフト)
- もっともらしい誤り(ハルシネーション)を利用者が信じて業務が誤る
- 敵対的な入力(プロンプトインジェクション等)で想定外の動作をする
- 利用者がAIの判断を覆せない(介入可能性の欠如)

### 3. 書き込む先

| 内容 | 書き先 |
|---|---|
| AI固有の失敗シナリオ | premortem.md |
| AI固有の品質特性(robustness・制御可能性等)の要否 | quality-characteristics.md |
| 評価セットの整備・段階的リリース(shadow/canary)の要否 | test-plan.md |
| 観点+オラクルの型 | test-design.md |
| 評価セットでの測定手順 / サンプリングレビューの設計 | test-cases.md |

shadow(ユーザー影響ゼロで新旧を比較)→ canary(実トラフィックの一部で実測)の順が定石。

## してはいけないこと

- 確率的な出力に単発の期待結果を書くこと(1回通った≠合格)
- 許容誤り率を決めずに「精度を確認する」と書くこと
- デモの成功例だけを証拠にすること(評価は固定した評価セットで)
- 規制・規程(EU AI Act等)の該当有無を確認しないこと

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
