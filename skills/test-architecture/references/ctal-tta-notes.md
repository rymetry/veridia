- 深さ: 本文精読(第0〜6章・付録Aまで通読。要約はAIによる。索引は除く)
- このノートの目的: test-architecture の対話で **「開発者側・技術側へ委譲する」判断の材料** を与える。
  TTA(Technical Test Analyst)が担う領域 = Veridia では多くを「委譲」として扱う領域なので、
  委譲先が何をどこまでカバーし得るか・実在確認で何を聞くべきかの視点で整理した。

## 第1章 リスクベースドテストにおけるTTAの役割(30分)

- TTAはテストマネージャの枠組みの中で **技術的リスク(セキュリティ・信頼性・性能)の
  「起こりやすさ(likelihood)」** を見積もる役。ビジネス影響はTest Analystの担当。
- 技術的プロダクトリスクの典型因子: 技術の複雑さ / コードの複雑さ / ソース変更量 /
  技術系欠陥の履歴 / インターフェース・統合の問題。
- **委譲判断への示唆**: 委譲先(開発者)に「変更量が多い箇所・複雑な箇所はどこか」を聞くと、
  委譲した領域の中でもリスクの濃淡が見える。委譲=一律に任せる、ではない。

## 第2章 ホワイトボックス技法(300分)— 委譲時の網羅レベル確認の核

### 強さの序列(subsumes 階層)

弱 → 強: **ステートメント < ブランチ/デシジョン < MC/DC < マルチプルコンディション**

- 上位を100%達成すれば下位は自動的に100%になる(subsumes)。
  なので網羅基準は **1つだけ指定すればよい**(ステートメント100%とMC/DC100%の併記は不要)。
- 網羅レベルを指定するなら **100%で指定するのが良い習慣**。80%指定だと「テストしにくい=
  複雑で欠陥が濃い残り20%」が未テストのまま残る。ISO 29119-4 は実行不能項目を分母から
  除外できるため100%は現実的な目標になる。

### 各技法の使い分け

| 技法 | 何を見るか | 使いどころ |
|---|---|---|
| ステートメント | 実行可能文を1回は実行 | 全コードの最低ライン |
| デシジョン(≒ブランチ) | 各判定のTRUE/FALSE両方 | 重要・クリティカルなコード |
| MC/DC | 各原子条件が単独で判定結果を変えること(N条件でN+1テスト) | 安全関連(航空・自動車)。デシジョンと全組合せの中間の現実解 |
| マルチプルコンディション | 原子条件の全組合せ(2^N) | 長期間无停止が求められる組込み等、まれ |

- 注意点: 条件のカップリング(同一変数の複数出現)や、コンパイラの短絡評価が
  MC/DC達成を妨げることがある。
- 通常は **ブラックボックステストを先に行い、カバレッジを測ってから不足分だけ
  ホワイトボックスで補う** のが標準的な流れ。
- 安全関連システムでは規格が網羅レベルを決める(IEC 61508のSIL 1〜4、ISO 26262、DO-178C)。
  例: SIL 3ならブランチ100%が事実上必須、SIL 4ならMC/DC100%。
- 非安全系での選定要因: 契約 / 顧客要求 / 規制 / 組織のテスト戦略 / コーディングスタイル
  (複合条件が無いコードにMC/DCは無駄)/ 欠陥履歴 / スキル / **測定ツールの有無**。

### APIテスト(2.7)

- 技法ではなく「テストの一種」。負のテスト(想定外入力・例外処理)が特に重要。
  見つかる欠陥: インターフェース不整合・データ処理・タイミング・トランザクション喪失/重複・例外処理。
- RESTなら入力網羅(全操作・全パラメータ・操作列)と出力網羅(全ステータスコード・全プロパティ)
  という網羅基準が存在する。公開APIほどリスクに応じて厚くする。

### 委譲の実在確認で聞くこと(第2章から)

1. ユニットテストの **カバレッジは測定されているか**(ツールが無ければ網羅は語れない)
2. 基準は何か(ステートメントか、ブランチか)。**「カバレッジ80%」なら残り20%が何かを聞く**
3. 複合条件を持つ判定ロジックがあるか。あるならデシジョンで足りるか
4. API境界の負のテスト(不正入力・例外・リトライ)は誰が見ているか

## 第3章 静的解析と動的解析(180分)

### 静的解析(実行せずに欠陥検出・保守性改善)

- **制御フロー解析**: 到達不能コード・呼ばれない関数・不正なループ等を検出。
  サイクロマティック複雑度を測り、高複雑度の部品はリファクタリング候補・欠陥集中の指標になる。
- **データフロー解析**: 変数の定義→使用→破棄の順序異常を検出
  (定義後未使用、未定義で使用、破棄後使用など)。限界: 実行時にしか決まらないパス、
  動的データ構造、**並行スレッド間で共有される変数** はツールでも検出困難。
- **保守性向上**: コーディング規約準拠チェック、重複コード検出、結合度/凝集度メトリクス。
  静的解析ツールの出力は「欠陥」ではなく **警告**(誤検知・要判断を含む)。
- Webコードのセキュリティ脆弱性(XSS、SQLインジェクション等)も静的解析で発見可能。

### 動的解析(実行して初めて見える failure)

- 見つかるもの: **メモリリーク**(本番で初めて顕在化しがち。GC言語でも起こる)、
  **ワイルドポインタ**(たまたま動く→ビルド変更で突然クラッシュ、が最も危険)、
  再現困難な間欠障害、性能ボトルネック(プロファイラ。実行時間の80%は20%の部品に集中)。
- 早期開始が推奨(これらの failure は発見も修正も最も高くつく)。

### 委譲の実在確認で聞くこと(第3章から)

1. 静的解析ツール(linter/SAST)は **CIで常時実行されているか**。警告はトリアージされているか
2. メモリ/リソースリークの検査は行われるか(長時間稼働が要件なら特に)
3. 間欠障害が出たとき動的解析で追える体制か
4. **静的解析は「実行しないと見えない欠陥」を見つけられない** — 静的解析がある、は
   動的な確認の代替にならない(逆も然り)

## 第4章 技術的品質特性のテスト(345分)— TTAの担当範囲

ISO 25010 のうちTTAが担うのは: **信頼性 / 性能効率 / セキュリティ / 保守性 / 移植性 /
互換性(共存)**。機能適合性・使用性・相互運用性はTest Analyst側。

- 共通の計画課題: 非機能要件はしばしば未文書(既存版をベンチマークにする手が有効)/
  **本番相当環境が必要**(縮小版・クラウド・仮想化で代替する場合は代表性に注意)/
  ツールと専門スキルの取得コスト / 本番データの利用は個人情報保護で制約(匿名化は非自明な作業)。
- **セキュリティ**: 脅威例 = 不正アクセス・XSS・バッファオーバーフロー・DoS・中間者攻撃・
  ロジックボム。計画の要点: コンポーネント〜システムの全レベル+**本番後も定期実施**、
  レビューと静的解析の併用が有効、**攻撃テストは書面での明示的許可が必須**(無許可だと法的リスク)、
  セキュリティ強化は性能・信頼性に副作用があるため改善後は再測定。手順: 情報収集→
  脆弱性スキャン(NIST/OWASP)→攻撃計画。
- **信頼性**: 成熟性(通常運用下の故障頻度。信頼度成長モデルは全テスト完了後に長期間必要)/
  可用性(MTTF/(MTTF+MTTR)。SLAで規定されがち)/ 耐障害性(**フォールトインジェクション** =
  障害を意図的に注入する負のテスト)/ 回復性(バックアップ・リストア、フェイルオーバー、DR訓練)。
  「何をfailureと数えるか」の事前合意が必須。
- **性能効率**: 時間挙動(応答時間・処理時間・スループット)/ 資源利用(CPU・メモリ・I/O・帯域)/
  容量(最大同時ユーザ等)。テスト種別: ロード(負荷を段階的に上げる)/ ストレス(限界超過 or
  資源を絞る)/ スケーラビリティ。目的は2つ — **受入判定** と **開発者へのボトルネック情報提供**。
  システムテスト段階が主だが、クリティカル部品はコンポーネントテストでも早期測定。
  結果次第でアーキテクチャ変更になり得るため早期開始が重要。
- **保守性**: 保守作業のしやすさ(analyzability/modifiability/testability/modularity/reusability)。
  主に静的(静的解析+レビュー)で早期から評価可能。動的側は保守手順書どおりの
  アップグレード等ができるかの確認(運用受入テストの一部になり得る)。
- **移植性**: インストーラビリティ(手順どおり入るか・失敗時に中途半端な状態を残さないか・
  アンインストール可能か)/ 適応性(全対象環境で動くか)/ 置換性(COTS部品の入替)。
- **互換性(共存)**: 同一環境に他アプリと同居して相互干渉しないか。**単独環境のテストでは
  検出できず、本番相当の同居環境で初めて分かる** — システムテスト完了後に実施が普通。
- **運用プロファイル(4.9)**: 想定ユーザ数・操作頻度のパターン定義。信頼性・性能テストの
  入力生成の土台。監視ツールの実測または業務側の見積りから作る。

### 委譲の実在確認で聞くこと(第4章から)

1. その品質特性の **要件・目標値は文書化されているか**(無ければ既存版ベンチマーク方式か)
2. 本番相当環境で測るのか。縮小環境なら結果の外挿方法は説明できるか
3. セキュリティテストの **実施許可** は書面で取れているか。実施後の性能再測定は予定されているか
4. 性能・信頼性の測定は誰の担当か(専門ツール・専門スキル前提。開発者のユニットテストでは代替不能)

## 第5章 レビュー(165分)

- TTAは技術レビューで運用(挙動)視点を提供し、チェックリストの定義・保守と欠陥重要度付けを担う。
- **準備時間が確保されないレビューは編集作業に堕ちる**。対象物単体でなく関連文書との整合まで見る。
- アーキテクチャレビュー例(Web性能): コネクションプーリング / ロードバランシング / キャッシュ /
  OLTP・OLAP分離など。コードレビューのチェックリストは言語固有・低レベルが有効
  (構造 / 文書化 / 変数 / 算術 / ループ分岐 / 防御的プログラミング)。
- **委譲判断への示唆**: 「コードレビューで見ている」と言われたら、チェックリストの有無と
  観点(性能・セキュリティを含むか)を確認する。レビューは静的テストの一形態であり、
  性能問題(非効率クエリ・リトライロジック)の早期検出に有効。

## 第6章 テストツールと自動化(180分)

- **テスト自動化プロジェクトはソフトウェア開発プロジェクトそのもの**(設計・レビュー・テストが必要)。
  アーキテクチャ無しの自動化はROIを回収できない。
- GUI経由よりAPI/CLI経由の自動化が保守に強い。データ駆動(データを外部化)→
  キーワード駆動(操作も抽象化)の順に保守性が上がるが初期コスト増。
  失敗時挙動と実行前後のシステム状態リセットを設計に含める。
- 特殊ツール: フォールトシーディング(テストの検出力評価)/ フォールトインジェクション /
  性能テストツール(プロトコルレベルで仮想ユーザ生成。プロトコル互換性が選定の鍵)/
  Webテストツール(リンク切れ・HTML検証・アクセシビリティ)/ MBTツール /
  **xUnit・CI/ビルドツール(開発者ツールだがTTAが保守することも多い)** /
  モバイルのエミュレータ・シミュレータ。
- **委譲判断への示唆**: 「CIで自動テストが回っている」と言われたら、失敗時に誰が調査するか・
  ビルド失敗がテスト環境への流入を止める構成かを確認する。
