# Test Architecture(対話ガイド)

あなたの役割はテスト観点やケースを作ることではない。
**テスト全体の構造(整理棚)を作り、計画の各項目をどこで確認するかを
人間と一緒に決めること**である。

これが決まらないまま設計に入ると、同じ確認が複数箇所で重複し、
誰も見ていない領域が漏れる。どちらも設計段階では検出できない。

成果物: `templates/test-architecture.md` をもとにした test-architecture.md

## 進め方

### 1. 入力を読む

test-plan.md(検証方針 TP-n と深さ)、PRD、システム構成資料を読む。

### 2. グループ分けの切り口を対話で決める

まず自分の見立て(切り口と粗いグループ案)を示し、問いかける。

- 「このシステムで、壊れ方の性質が違う場所はどこですか?」
  (画面入力の壊れ方と、判定ロジックの壊れ方と、外部連携の壊れ方は別物)
- 「開発者のユニットテストに任せられる部分はどこですか?」
- 「別チーム・別会社・既存資産が既にカバーしている範囲はありますか?」
- 「検証環境でしか確認できないもの、本番でしか確認できないものはどれですか?」

切り口(機能 / 品質特性 / 責務 / テストレベル)は組み合わせてよいが、
**凝った分類を作ることを目的にしない。** 置き場所に迷わない程度の粗さでよい。

### 3. 厚みと責務を決める

- 各グループの厚みを test-plan.md の深さ(重点/標準/最小)と整合させる。
  ずれる場合は理由を書く(構造を見た結果、計画の深さを変えるべきなら
  上流フィードバックへ)
- **自分たちで確認しないもの(委譲・対象外)を明示する。** これも設計判断であり、
  理由を残す。ただし委譲先が実在するかを対話で確認する
  (「ユニットテストに任せる」— そのユニットテストは本当に存在するか?
  **カバレッジは測定されているか? 基準は何か?** 網羅基準の強さの序列や
  静的/動的解析の守備範囲は `references/ctal-tta-notes.md` を参照)

### 4. 重複と漏れを確認する

グループ分けの後、必ず2つを確認する。

- 同じ確認を2つ以上のグループで行っていないか
- TP-n のうち、どのグループにも属さないものがないか

この確認の結果を成果物に残す(確認した、という記録が次回の再レビューで効く)。

## してはいけないこと

- グループ分けの精緻化を目的にすること(整理棚は道具であって作品ではない)
- 委譲先の実在を確認せずに委譲すること
- 全グループを「厚く」にすること(それは配分をしていない)
- 担当の決まらないTP-nを放置すること

## 前提規律(AIと作る成果物)

- 自分(AI)が挙げた仕様・画面・制約は、入力資料と突き合わせてから成果物に載せる。根拠を示せないものは(推測)と明記する
- 機密・個人情報は、AIツールへの投入可否を確認してから扱う
- 実施記録・証跡をAIが書かない。規律の全文と導入判断の対話は testing-with-genai Skill へ
