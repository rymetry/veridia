## 第1章 基本概念

- 性能効率は ISO 25010 の3サブ特性で捉える: **時間挙動**(応答時間)/ **資源利用**(CPU・メモリ等)/ **キャパシティ**(ユーザー数・データ量の上限)。どれを重視するかはリスク次第
- 性能テストの原則: ステークホルダー期待に整合 / **再現可能**(同一システムで統計的に同一の結果) / 結果が理解・比較可能 / 本番代表環境で / 予算・期間内で実行可能
- 負荷種類(7種。全部やらず目的に対応するものだけ):
  - **load**: 想定される現実的な負荷の増加に耐えるか
  - **stress**: 想定上限またはそれ以上のピーク。資源削減時(帯域・メモリ減)の挙動も含む
  - **scalability**: 将来の成長(ユーザー・データ増)に耐えるか。限界が分かれば本番監視の閾値を設定できる
  - **spike**: 瞬間集中への正しい応答と、その後の**定常状態への復帰**
  - **endurance**: 連続稼働での安定性。メモリリーク・DB接続・スレッドプール枯渇の検出
  - **concurrency**: 同時同一操作(一斉ログイン等)。再現が特に困難
  - **capacity**: 何ユーザー・何トランザクションまで目標性能を満たせるか
- **静的テストが機能テスト以上に重要**: 性能欠陥の多くはアーキテクチャ・設計段階で混入。要求・DBスキーマ・システム/ネットワーク構成・重要コードのレビューで早期発見できる
- 負荷生成の4方式: UI経由(少数ユーザーのみ実用的)/ クラウドソーシング(実ユーザー多数だが再現性低)/ **API経由**(UI変更に強い)/ **プロトコル記録・再生**(大規模・再現性高。主流)
- 共通の故障モード4分類(premortemの種に使える):
  1. 全負荷レベルで遅い → DB設計不良・ネットワーク遅延
  2. 中〜高負荷で劣化 → 資源飽和・背景負荷の変動
  3. **時間経過で劣化** → メモリリーク・ファイル/DB肥大・断片化
  4. 高負荷時のエラー処理が破綻 → プール不足・キュー過小・タイムアウト設定が急すぎ

## 第2章 測定の基礎

- メトリクスなしの性能テストのリスク: 合格が判断できない / 傾向が読めない / **個人の主観で評価される** / ベースライン比較ができない
- メトリクスは3環境で分類: **技術**(応答時間・資源利用率・スループット・バッチ処理時間・エラー数)/ **ビジネス**(業務プロセス速度・時間あたり処理件数・SLA違反率・同時利用者数)/ **運用**(起動・バックアップ・復元・アラート発報時間)
- 取りすぎない: メトリクスごとに収集・報告の仕組みが要る。目的に効く最小集合を定義(Goal-Question-Metric が参考になるが万能ではない)
- 測定自体が性能に影響する「**プローブ効果**」を最小化する
- 結果の入手源は3つ: 性能テストツール / 監視ツール / **ログ分析**(資源枯渇・メモリエラー・デッドロック・SQLタイムアウトはサーバーログに出る)
- 生の集計結果は誤解を招く: 資源利用率が全て75%未満でも、主要トランザクションが桁違いに遅いことがある。集約は総合像の伝達のためで、詳細確認の代わりではない

## 第3章 ライフサイクルでの性能テスト

- 性能テストは**反復的**: 1回のテスト→調整→次のテストのサイクル。ISTQBテストプロセス(計画〜完了)に沿う
- テスト分析で決めること: 負荷レベル・タイミング条件・対象トランザクション・負荷種類の選定。これがこのSkillの対話の中心
- アーキテクチャ別の典型リスク: 単一マシン(リーク・非効率アルゴリズム)/ 多層(DB設計・ネットワークボトルネック)/ 分散(不安定なリモートサーバー)/ 仮想化(ホスト資源の取り合い・設定ミス)/ クラウド(自動スケール設定の誤り)/ クライアントサーバー(接続品質・LB)/ モバイル(資源変動・電池・センサー)/ 組込みリアルタイム(遅延が安全性に直結)/ メインフレーム(API公開による想定外負荷)
- リスク分析は**早期に開始し繰り返す**。システムテスト末期の性能テスト頼みは典型的失敗(後期発見はプロジェクト中止級のコスト)
- 残存リスクは具体的に伝える: 「まだ遅延の可能性はある」ではなく「**閾値X秒超の遅延を経験する顧客の割合**」で示す
- 反復開発では: 性能要件は非機能ユーザーストーリーの受け入れ基準に書く。CIに入れる性能テストは専任チームの本格テストの**サブセット**(ビルド単位で回せる規模に絞る)
- COTS/外注でも性能検証責任は買い手にある。契約に性能要件と受け入れ基準を明記

## 第4章 性能テストのタスク(中心章)

### 計画
- 目的は**ユーザー基点**(体感・業務目標)と**技術基点**(スケール限界・劣化条件)を分けて定義
- 性能テスト計画(PTP)の構成: 目的 / システム概要 / 負荷種類 / **受け入れ基準** / テストデータ / システム構成 / 環境 / ツール / プロファイル / メトリクス / リスク
- 覚えやすい対応: **応答時間=ユーザーの関心、スループット=ビジネスの関心、資源利用=システムの関心**
- 受け入れ基準の根拠: テスト目的 / SLA / **ベースライン**(過去測定との比較基準)
- テストデータ: 本番からの抽出・匿名化(GDPR必須)。ただし**マスキングはデータ特性を変え結果を歪めるリスク**がある、と明記されている
- ステークホルダー説明はビジネス系(リスクとテスト目的の対応・費用対代表性)と技術系(負荷生成方法・再現手順・環境共有の調整)で内容を変える

### 分析・設計・実装(ワークロードモデリングの手順)
1. **オペレーショナルプロファイル**を作る: ユーザー種別(ロール)ごとの典型操作パターン。データ源=関係者インタビュー / 要求・ユーザーストーリー(As a <user>がそのまま使える)/ 既存システムの利用ログ / ユーザー行動観察
2. トップダウンで粗く作り、目的達成に必要な分だけ細分化。**高頻度・高リスク・大データ量**の操作を優先
3. **ロードプロファイル**に合成: どのプロファイルを何インスタンス(仮想ユーザー)、どんな時間分布で流すか。パターンは ramp-up / ramp-down / ステップ投入 / 業務サイクル模倣。例: 背景負荷100VU一定+220VUランプアップの重ね合わせでストレス状態を作る
- **スループットと同時ユーザー数を混同しない**(本文の核心): 同じ500ユーザーでも毎分1クエリと毎時1クエリでは負荷が60倍違う。ユーザー数だけでは負荷を定義できない。式: スループット = 仮想ユーザー数 ÷ (処理時間 + シンクタイム)。処理時間が伸びるとスループットは勝手に落ちる
- ユーザーがいないシステム(バッチ・システムオブシステムズ)にもプロファイルは必要: バッチは処理種別ごとの経路と**時間窓内に完了できるか**が焦点
- スクリプト実装の落とし穴: 記録スクリプトは**相関**(セッションID等の変数化)を怠ると動かない。全ユーザーが同一アカウント・同一データだと**キャッシュで楽観的すぎる結果**か**ロック競合で悲観的すぎる結果**になる → データのパラメータ化が必須
- 環境準備: **性能は環境の非線形関数**。本番との差が大きいほど外挿の信頼性が落ちる。差がある場合は差の内容と外挿方法を計画に書く。使えない外部コンポーネントはスタブ化(サービス仮想化)。負荷生成マシン自体も監視する(生成側がボトルネックになる事故を防ぐ)

### 実行と分析
- 測定は**定常状態**で行う。ramp-up/down中は挙動が変わるので平均監視は誤解を招く(spike等、過渡状態を意図的に測る場合は特に注意)
- 全ツールの**時刻同期**をしないと事後分析でログを突き合わせられない
- 結果分析の順序: まず**仮想ユーザーの成否**を見る(失敗があると他の数値が全て歪む。失敗トランザクションは所要時間が短く出るためTPSも無効になる)→ 応答時間 → TPS → エラー → スループット
- 応答時間の評価: **平均は外れ値に歪められる。90パーセンタイルを目標に使う**のが通例。100%遵守は要求しない(コストに見合わない)
- メトリクス間の**相関**で劣化点を特定する(例: CPU90%到達時のTPSはいくつだったか)
- レポート: エグゼクティブサマリ / ベースライン比較付き結果 / テストログ(日時・構成・スクリプト・データ・変更点)/ 推奨アクション。**テスト間の構成変更は必ず記録**

## 第5章 ツール

- 構成要素は3つ: 負荷生成器 / 管理コンソール(開始停止・集計)/ 監視ツール(本番監視に転用可)
- 選定基準: **プロトコル対応**(最重要。4.2.1のOSIレイヤ5-7が主戦場)/ プラットフォーム互換 / スケール上限(ライセンス数・生成マシン要件・多拠点生成)/ 使い手のスキルとの整合(スキル不足の設定ミス→不正確な結果)/ 監視の十分性
- ツールはプロジェクトでなく**組織のために選ぶ**。習熟の時間と予算を計画に入れる
- シラバスは特定製品名を挙げていない(ライセンス形態の分類のみ: 買い切り / クラウド従量 / OSS)

**反映状況(2026-08-16)**: 全3件反映済み(1 負荷モデル対話の操作頻度 / 2 90パーセンタイル
等の分布判定 / 3 故障モード4分類)

1. **「同時ユーザー数だけでは負荷を定義できない」を負荷モデル対話に追加**: 同じ500人でも操作頻度で負荷が60倍違う(4.2.5)。現在の質問「何人が何をしますか?」に「**その操作をどのくらいの頻度で?**」を足すだけで負荷モデルの精度が大きく変わる
2. **判定基準は平均でなく90パーセンタイル、100%遵守は求めない**(4.4): SKILL.mdの「判定基準は数値で」に統計の取り方が欠けている。平均は外れ値で歪むため「ピーク負荷で90%のユーザーが◯秒以内」の形を推奨し、100%要求はコスト過大と明記できる
3. **共通故障モード4分類をpremortem対話の呼び水に**(1.5): 「全負荷で遅い/高負荷で劣化/時間経過で劣化/高負荷時のエラー処理破綻」は失敗シナリオ出しの網羅チェックとしてそのまま使える(特に「時間経過で劣化」= endurance の必要性判断に直結)
