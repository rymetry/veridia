# Performance Testing(対話ガイド)

あなたの役割は負荷試験を実行することではない。
**「どんな負荷で・何を測り・いくつなら合格か」を対話で確定させること**である。
これが決まっていない性能テストは、実行しても合否が出ない。

新しい成果物は作らない。既存の成果物の該当箇所に書き込む。

## いつ使うか

- quality-characteristics で Performance Efficiency が採用されたとき
- premortem に性能起因の失敗シナリオがあるとき
- 応答遅延・大量データ・同時アクセスがプロダクトの前提にあるとき

## 進め方

### 1. 負荷モデルを対話で作る(最重要)

- 「ピークはいつ、何人が、何をしますか?」(月末の申請集中、始業直後 等)
- 「データは何年でどこまで増えますか? 増えた状態で試せますか?」
- 「一番遅くなると困る操作はどれですか? 何秒なら許せますか? それは誰が決めましたか?」

負荷の種類は狙いに合わせて選ぶ: 想定負荷(load)/ 限界(stress)/ 瞬間集中(spike)/
連続稼働(endurance)/ 容量(capacity)。全部やらない。失敗シナリオに対応するものだけ。

### 2. 書き込む先

| 内容 | 書き先 |
|---|---|
| 性能の失敗シナリオ(根拠=データ量・利用者数) | premortem.md |
| 検証の深さ・負荷の種類・環境制約(本番相当データはいつ用意できるか) | test-plan.md |
| どの環境・どのレベルで測るか | test-architecture.md |
| 観点+**数値の判定基準**(応答時間・スループット・エラー率) | test-design.md |
| 測定手順・負荷条件・結果 | test-cases.md |

### 3. 判定基準は数値で

- 「速いこと」は観点ではない。「◯◯操作がピーク負荷で◯秒以内」まで落とす
- 基準の出どころ(要求・現行実測・業界慣行)を rationale に残す
- 測定環境が本番相当でない場合、**その差を必ず記録する**(結果の解釈が変わる)

## してはいけないこと

- 合格基準なしの負荷試験(「測ってみましょう」で終わる)
- 本番と異なる環境での結果を無条件に本番へ外挿すること
- 全種類の負荷テストを網羅しようとすること
- ツール選定を目的化すること(まず何を測るかが先)
