## この文書の役割

テスト計画の各項目(TP-n)を、テストアーキテクチャのグループ(A-n)に沿って、
**何を確認すれば検証したことになるか**(テスト観点)へ展開する。
個々の手順・入力値まではここでは書かない(テストケースの仕事)。

## テスト観点

| # | 対応 | 場所 | 確認する観点 | 判定方法 | 使った技法 |
|---|---|---|---|---|---|
| TD-1 | TP-1 | A-3 | 例: 本番同等のSAML設定でログインが成功し、主要画面まで到達できる | 明確(成功/失敗が自明) | — |
| TD-2 | TP-1 | A-3 | 例: 認証失敗時に失敗種別がログで識別できる | 明確 | エラー推測 |
| TD-3 | TP-2 | A-1 | 例: カード番号がブランドごとの正しい桁数のみ受け付けられる | 明確 | 同値分割・境界値 |
| TD-4 | | | | | |

- 場所列(A-n)は test-architecture.md のグループ。**どのグループにも置けない観点が
  出たら、アーキテクチャの見直しを対話で提起する**(観点を無理に押し込まない)
- ④を③に畳んだ構成(test-architecture.md を作らない場合)は、この列に
  テストレベル(例: 結合 / システム)を直接書く。見直しの提起先は test-plan.md

判定方法は2択で書く:

- **明確** — 期待結果が事前に定義でき、成功/失敗が機械的に判定できる
- **人の判断** — 仕様の妥当性・使い勝手など、人が見て判断する必要がある

「人の判断」を無理に「明確」と書かない。判定できない観点に推測で
期待結果を作ることが、テストで最も危険な失敗である。

技法(境界値、状態遷移、デシジョンテーブル等)は、観点を導くのに使った場合だけ書く。
全部の観点に技法が要るわけではない。

## パラメーターと値候補

観点のうち、**入力・状態・環境によって結果が変わるもの**について、
何を変えて試すか(パラメーター)と値候補を決める。ここを飛ばしてケースを
書き始めると、ケース数が爆発するか、逆に代表値1つで済ませてしまう。

| 対応 | 変える要素 | 値候補 | 組み合わせの絞り方 |
|---|---|---|---|
| TD-3 | 例: カード番号の桁数 / ブランド | 13〜17桁 / VISA・Master・AMEX・Diners | ブランドごとに正しい桁数が違うため単純な総当たりにせず、桁数判定が目的の組だけ作る(有効期限は「有効」に固定) |

- **全組み合わせをそのまま試さない。** 技法(境界値・ペアワイズ等)や仕様の理解で絞り、
  **絞った理由を必ず書く**(理由のない絞りは漏れと区別できない)
- 仕様に書かれていなくてもバグが出そうな要素(連打、同時操作、空値)は対話で確認して追加する
- 単純な観点(パラメーターが実質ないもの)はこの表に載せなくてよい
