## 前提

「このプロジェクトは失敗した」と仮定し、なぜ失敗したのかを遡って挙げる。

- 技術の失敗だけでなく、価値(作ったが使われない)・進行(間に合わない)・
  体制(人が足りない)・外部依存の失敗も対象にする
- 件数は重要なもの5〜10件に絞る。網羅より根拠の質を優先する

## 失敗シナリオ

| # | 失敗シナリオ | 根拠(入力資料のどこか) | 影響 | 起きやすさ |
|---|---|---|---|---|
| P-1 | 例: リリース後、SSOでログインできず誰も使えない | PRD 4.1 認証 / SSO検証環境は2週間前からという制約 | 高 | 中 |
| P-2 | | | | |

- **根拠には、入力資料の中の具体的な箇所を書く。** 一般論(「外部APIは不安定」)は根拠にならない
- 入力資料に根拠がない懸念は捨てなくてよい。ただし根拠欄に **(推測)** と明記する
